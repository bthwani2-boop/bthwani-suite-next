# ORCHESTRATOR AUTHORITY DISPOSITION — `g`

## 0. Purpose

This file exists to prevent the `g` cleanup/restructure plan from becoming a second governance system.

Canonical execution/closure authority remains the latest live:

`tools/prompting/bthwani-orchestrator/00-ORCHESTRATOR.md`

plus routed `01–05` and material focus modules.

This plan package is subordinate execution context only.

## 1. No parallel governance

Do not create or maintain a second:

- orchestrator;
- product/system authority;
- engineering authority;
- progress registry;
- closure registry;
- ownership ledger;
- compatibility ledger;
- evidence ledger;
- migration authority;
- filesystem authority;
- root database.

If the live orchestrator already defines the required law, reference/apply it. Do not copy it into a competing canonical document.

Execution notes may temporarily record root-specific facts, but they must remain subordinate to live code/evidence and may not redefine truth.

## 2. What this package is allowed to add

This package may provide campaign-specific operational context that the live orchestrator does not need to permanently own, such as:

- branch role: `g = dedicated radical cleanup/restructure branch`;
- current audit pin and root reclassification;
- current exact-HEAD execution protocol;
- campaign-specific root queue;
- artifact dispositions for the active affected cone;
- expected deletion/migration lists;
- evidence invalidation for a current closure unit.

These are not global authorities. They are refreshed from live repository truth.

## 3. Single mutation authority

For the active `g` campaign:

```text
EXECUTION_MODE=SINGLE_SESSION_DIRECT_ON_G
TARGET_BRANCH=g
ACTIVE_MUTATION_SESSIONS=1
```

Read-only sub-agents may inspect/falsify in parallel. Material mutation authority remains one.

Any future multi-agent write protocol is **not active** unless a human explicitly changes execution mode and the live orchestrator allows it.

No Session A/B/C, temporary mutation branches, or parallel worktree ownership lanes may be inferred from older plan text.


This is a concurrency check, not a new governance authority.

## 6. Compatibility disposition

Compatibility is not a permanent layer by default.

If a compatibility path must temporarily remain during migration, record only:

```text
COMPAT_PATH=
WHY_ATOMIC_MIGRATION_IS_IMPOSSIBLE=
REQUIRED_CONSUMERS=
CANONICAL_AUTHORITY=
MUST_NOT_WRITE_OR_REDEFINE_TRUTH=
REMOVAL_TRIGGER=
EXPECTED_RETIREMENT_BOUNDARY=
```

Once consumers are migrated, delete the compatibility path and remove the temporary record.

Do not maintain a permanent compatibility ledger merely to document residue that should have been removed.

## 7. Filesystem disposition

The live repository structure after closure is the primary evidence of filesystem authority.

During a root, record each material artifact disposition only as needed to execute:

`KEEP_PROVEN`, `REHOME`, `MERGE`, `SPLIT`, `REWRITE`, `REGENERATE`, `DELETE`, `BOUNDED_RETIREMENT`.

After cutover/deletion, do not preserve obsolete plan inventories as a parallel structural truth unless they are required evidence under the live orchestrator.

## 8. Evidence disposition

Evidence is consumed, not accumulated indefinitely.

For every material evidence item:

`SOURCE → EXACT_SHA/CONTEXT → FINDING → VALIDATE/FALSIFY → ROOT MAPPING → ACTION → STATUS`.

Once a root is closed on a newer exact SHA, stale evidence is historical context only. It cannot keep an already disproven/open state alive.

Conversely, stale PASS evidence cannot close a newer candidate.

## 9. Plan self-cleanup law

Because `g` is a cleanup/restructure branch, this plan package itself is subject to the same zero-residue rules.

Therefore:

- filenames that encode obsolete execution modes must be renamed/deleted;
- sections that propose already-existing orchestrator laws as new authorities must be removed;
- contradictory branch identities must be removed;
- stale root statuses must be reclassified;
- duplicate instructions between plan files should be collapsed to references where possible;
- once the campaign is complete, decide whether this plan remains required evidence or should be deleted/archived outside live authority paths according to repository governance.

The plan cannot demand zero repository noise while preserving its own obsolete noise.

## 10. Escalation to orchestrator changes

Do **not** edit the orchestrator merely because this campaign needs a temporary execution detail.

An orchestrator change is justified only if a fresh independent audit proves a reusable governance defect in the live orchestrator itself that materially affects correctness beyond this campaign.

If such a defect is proven:

1. identify exact missing/contradictory law;
2. prove it is not already covered by existing routed modules;
3. change the smallest canonical orchestrator location;
4. delete any plan-level duplicate authority created as a workaround;
5. verify the orchestrator remains singular and coherent.

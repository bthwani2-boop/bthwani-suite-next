ثبّتُّ الصياغة على الحالة الريموت الحالية للفرع `abbas` عند SHA ‏`e739bbc23ebde37b93f2347bf4c287146d7c9081`. الإطار الحالي يفرض `COVERAGE.json` كمصدر التغطية المنظم الوحيد، ووحدة غير متداخلة لكل شأن تنفيذي، ووحدة كتابة واحدة فقط `IN_PROGRESS`.   كما أن الملف التنفيذي العام نفسه يقر بأنه لا يتجاوز ترتيب السلطة الحي، ويعرّف «الدقة الكاملة» بوصفها دقة مثبتة لا ادعاءً لفظيًا. 

وأتعامل في الصياغة التالية مع `smsm-dsh-wlt-journeys` **كمصدر تشخيص ومقارنة واكتشاف لا كحقيقة نهائية**؛ فهي نفسها مصنفة `DERIVED_SUPPORT_ARTIFACT`. أما تقسيمها إلى 24 شريحة و107 رحلات فيستخدم كعدسة قوية لا كافتراض يجب فرضه على الواقع.    والمولد الحالي يؤكد `--surface` كاسم تقني للمدخل مع دعم `--repository`. 

## الأمر الأول — إعداد حزمة التشخيص وخط الأساس وخطة التنفيذ

# الأمر النهائي الحاكم لإعداد حزمة تشخيص وخط أساس وخطة تنفيذ مكتفية ذاتيًا

## 0. مدخلات المهمة

```text
المستودع: <OWNER/REPOSITORY>
الفرع أو المرجع: <BRANCH_OR_REF>
اسم الحزمة: <TASK_NAME>

نوع نقطة البداية:
<JOURNEY | APPLICATION | SURFACE | SECTION | PAGE | FEATURE | FILE | SERVICE | DOMAIN | OTHER>

نقطة البداية:
<TARGET>

النتيجة التشغيلية المطلوبة:
<MEASURABLE_OBJECTIVE>

تفويض تسليم الحزمة:
<NO_COMMIT | COMMIT | COMMIT_AND_PUSH>
```

نفّذ عبر GitHub Remote **مرحلة التشخيص والتخطيط وإعداد الحزمة فقط**. لا تنفذ في هذه المرحلة تصحيحات تشغيلية في كود المنتج أو العقود أو قواعد البيانات أو الهجرات أو Runtime أو الاختبارات أو الحوكمة خارج مجلد الحزمة.

الهدف هو إنتاج حزمة يستطيع وكيل تنفيذ آخر استخدامها مباشرة دون إعادة اكتشاف النطاق أو تخمين المعمارية أو اختيار مالك الحقيقة أو اختراع الاختبارات أو إعادة تقرير شروط الإغلاق.

---

# 1. المبدأ الأعلى للدقة

تعامل مع المهمة كما لو أنها تخضع في وقت واحد لمراجعة معماريين ومهندسي Backend وFrontend وMobile وقواعد بيانات وأمن وأنظمة موزعة وRuntime وSRE وQA وUX وحوكمة، لكن لا تستبدل ذلك بادعاءات لفظية عن نسبة الدقة.

تعني الدقة المطلوبة عمليًا:

```text
ZERO_FALSE_SUCCESS
ZERO_UNASSESSED_REQUIRED_SCOPE
ZERO_UNMAPPED_RELATED_CONCERN
ZERO_UNOWNED_WRITE_PATH
ZERO_UNJUSTIFIED_PARALLEL_TRUTH
ZERO_UNPROVEN_CLOSURE
```

لا تعتمد أول تفسير يبدو صحيحًا ولا أول تقرير ولا أول سجل رحلات ولا أول وثيقة تصميم.

استخدم:

```text
DISCOVER
→ DIAGNOSE
→ CROSS-CHECK
→ CHALLENGE
→ RE-DIAGNOSE
→ PLAN
→ VERIFY PLAN
```

حتى يصبح التشخيص والخطة صالحين للتنفيذ بالأدلة.

# 2. تثبيت الحقيقة الريموت

قبل أي تشخيص:

1. اجلب أحدث رأس ريموت للفرع أو المرجع المحدد.
2. تحقق أن المرجع المطلوب موجود فعلًا.
3. ثبّت SHA كاملًا بطول 40 حرفًا:
   `PINNED_REMOTE_SHA`.
4. ابنِ كل أدلة الحزمة على هذا الـSHA.
5. لا تستخدم الذاكرة أو نسخة محلية أو محادثة أو تقريرًا سابقًا لإثبات واقع المستودع.
6. أي معلومة من مصدر سابق تُعامل كفرضية حتى يعاد إثباتها على SHA المثبت.

لا تضع SHA ثابتًا داخل الأمر الدائم.

# 3. طبقات السلطة والأدلة — لا تخلط بينهما

افصل بين:

## أ. السلطة المعيارية: ما الذي يجب أن يكون

ابدأ وفق ترتيب السلطة الفعلي الموجود على SHA المثبت، وبالحد الأدنى:

```text
تعليمات المستخدم الحالية والتفويض
→ governance/authority/authority-precedence.json
→ AGENTS.md
→ Product Truth والسياسات الآلية الحية
→ العقود الحاكمة والحدود الرسمية للمجالات
```

إذا كشف المستودع ترتيبًا أكثر تحديدًا، طبقه.

## ب. أدلة التنفيذ: ما الموجود فعليًا

استخدم لتشخيص الواقع:

```text
الكود
→ العقود والعملاء المولدين
→ migrations / schema / constraints
→ الخدمات والـhandlers والـrepositories
→ Runtime configuration
→ الاختبارات
→ Events / Jobs / Integrations
→ Persisted readback
→ Cross-surface behavior
→ logs / metrics / traces عند توفرها
```

لا تجعل الواقع الخاطئ يتغلب على Product Truth، ولا تجعل وثيقة نظرية غير منفذة دليلًا على أن المنتج يعمل.

```text
CONTRADICTED

UNPROVEN
NOT_APPLICABLE
```

هذه تصنيفات تشخيصية نصية، وليست enums جديدة تضاف إلى مخطط `COVERAGE.json`.

# 6. إنشاء الحزمة من الإطار الحالي فقط

أنشئ الحزمة حصريًا داخل:

```text
tools/diagnose-implementing/<TASK_NAME>/
```

واستخدم فقط:

```text
tools/diagnose-implementing/_template/
tools/diagnose-implementing/new-package.mjs
tools/diagnose-implementing/new-unit.mjs
tools/diagnose-implementing/validate-package.mjs
```

يُمنع إنشاء Framework موازٍ أو العودة إلى:

```text
topics/
contexts/
journeys/
```

كأشجار مستقلة مكررة للحزمة.

استخدم:

```powershell
node tools/diagnose-implementing/new-package.mjs `
  --name <TASK_NAME> `
  --branch <BRANCH_OR_REF> `
  --sha <PINNED_REMOTE_SHA> `
  --surface "<TARGET>" `
  --objective "<TARGET_KIND>: <MEASURABLE_OBJECTIVE>" `
  --repository <OWNER/REPOSITORY>
```

`--surface` اسم تقني للمدخل الحالي فقط. لا تستنتج منه أن الهدف Surface؛ وثّق النوع الحقيقي والهدف في `MANIFEST.json` والنص التشخيصي بالقدر الذي يسمح به المخطط الحالي.

لا تغيّر `schemaVersion`، ولا تضف حقول JSON إلزامية غير مدعومة، ولا تنشئ مصدر حقيقة منظمًا ثانيًا.

# 7. الفصل الصارم بين نطاق التشخيص ونطاق التنفيذ

طبّق:

```text
DIAGNOSIS_SCOPE
= المستودع كله بالقدر الضروري لاكتشاف العلاقات والفجوات.

EXECUTION_SCOPE
= الهدف + كل اعتماد مثبت مباشر أو انتقالي
  + كل أساس مشترك يلزم استقراره لإغلاق الهدف.
```

لا تحول كل مشكلة في المستودع إلى وحدة تنفيذ.

يصبح العنصر `RELATED` عندما يثبت أنه:

- يملك الحقيقة أو السياسة أو الكتابة.
- يكتب أو يقرأ الحالة.
- يشتق قرارًا منها.
- يسبق الرحلة أو يبدأها أو يكملها.
- يعتمد على نتيجتها.
- يتأثر بفشلها.
- يدير النتيجة في Surface آخر.
- يستهلك العقد أو العميل أو الخدمة أو الجدول أو الحدث نفسه.
- يعتمد على Identity أو Permission أو Assignment أو Trusted Scope نفسه.
- يحمل أثرًا ماليًا أو تشغيليًا أو أمنيًا أو تدقيقيًا.
- يحتوي نسخة Legacy أو محلية أو موازية من الحقيقة.
- يلزم اختباره لإثبات الإغلاق.

المشكلة غير المرتبطة:

```text
assessment: DEFECT_OUTSIDE_EXECUTION_SCOPE
```

مع:

- الدليل.
- سبب الاستبعاد.
- أثر عدم المعالجة.
- شرط إعادة الفتح.

والاعتماد الخارجي:

```text
assessment: EXTERNAL_DEPENDENCY
```

مع دليل وشرط إعادة فتح.

# الأمر النهائي الحاكم لتنفيذ الحزمة أو المهمة المباشرة حتى الإغلاق المثبت

# 11. PHASE-00 — Foundation Gate

عندما تتضمن المهمة Journey أو Application أو Surface أو Feature عابرة للأسطح:

يُمنع بدء Journey execution قبل إغلاق Foundation المطلوب للمهمة.

شغّل في البداية:

```powershell
pnpm run guard:foundation
```

إذا كان موجودًا ومنطبقًا.

سجّل نتيجته.

فشله الأولي:

```text
DIAGNOSTIC EVIDENCE
```

وليس:

```text
STOP
```

نفّذ أولًا:

```text
FOUNDATION
MIGRATION
SHARED_PREREQUISITE
```

ثم Foundation Verification Unit.

أعد:

```powershell
pnpm run guard:foundation
```

لا تبدأ أول Journey مرتبطة حتى تنجح البوابة المطلوبة.

---

# 12. Foundation Closure Criteria

يجب ألا يبقى متعلقًا بالمهمة:

```text
FOUNDATION_BLOCKER
blocking SHARED_PREREQUISITE
parallel canonical truth
unowned write
untrusted permission/scope path
broken central contract
drifted generated client
required migration without proof
cross-surface shared state contradiction
forbidden dependency
foundational runtime failure
unmapped foundational dependency
foundation unit without required verification
```

سجّل SHA الناتج عن Foundation Gate بوصفه:

```text
JOURNEY_EXECUTION_BASE_SHA
```

في ملفات النتائج/الإغلاق الحالية، دون اختراع حقل Schema إلزامي جديد.

---

# 13. المجدول التنفيذي

لا تتبع رقم الوحدة فقط.

من الوحدات التي أصبحت dependencies الخاصة بها `DONE` اختر بالترتيب:

```text
1. critical path
2. unlocks most journeys
3. unlocks most surfaces
4. shared central repair preventing repeated work
5. high-risk/high-uncertainty work
6. small high-impact work
7. minimizes reopening stabilized contracts/schema/files
8. lower verification cost when equivalent
9. cleanup/non-blocking debt last
```

لا تبدأ وحدة تعتمد على Foundation غير مستقر.

---

# 14. التوازي الآمن

حافظ على:

```text
MAX_WRITABLE_IN_PROGRESS_UNITS = 1
```

يمكن توازي:

- reading.
- searching.
- dependency analysis.
- evidence gathering.
- independent static checks.
- independent package tests.

لا توازِ:

- conflicting writes.
- shared truth changes.
- contract generation.
- migrations.
- backfills.
- shared schema changes.
- unit commit/update state.

---

# 15. دورة تنفيذ الوحدة

لكل Unit:

## Preflight

تحقق من:

- paths.
- symbols.
- owner.
- coverage links.
- dependencies.
- current SHA.
- evidence freshness.

## Start

اجعل الوحدة الوحيدة:

```text
IN_PROGRESS
```

## Execute

نفّذ Tasks حسب `order`.

لكل Task:

1. افهم `currentProblem`.
2. تحقق من Root Cause.
3. نفّذ `requiredChange`.
4. حقق `targetState`.
5. حافظ على `mustNotChange`.
6. حدّث جميع Writers/Readers/Consumers.
7. نفّذ Migration قبل إزالة القديم.
8. نفّذ verificationIds.
9. لا تنتقل إذا بقي failure مانع.

## Result

سجل النتيجة الحقيقية.

لا تجعل الوحدة `DONE` إلا بعد:

- all tasks complete.
- all required checks PASS.
- valid resulting SHA.
- zero unresolved blockers.
- zero unresolved deviations.
- decision PASS.

# 32. أقصى تقدم ممكن

إذا وُجد مانع خارجي في مسار واحد:

# 33. `BLOCKED_WITH_EXPLICIT_CAUSE` ملاذ أخير

لا يجوز استخدامه بسبب:

```text
Bug
Build failure
Test failure
Lint failure
Type failure
Guard failure
fixable migration failure
fixable runtime configuration
contract mismatch
UI gap
missing implementation
cross-surface gap
internal technical debt related to target
newly discovered gap
incomplete plan
problem complexity
```

هذه كلها:

```text
DIAGNOSE → FIX → VERIFY → REPEAT
```

يسمح بـ:

```text
BLOCKED_WITH_EXPLICIT_CAUSE
```

فقط إذا ثبت جميع الآتي:

1. كل الإجراءات الداخلية الآمنة الممكنة استنفدت.
2. السبب المتبقي خارجي حقيقي أو تفويض مفقود لا يجوز تجاوزه.
3. لا يوجد Workaround آمن يحافظ على صحة النظام.
4. تم إنجاز كل العمل المستقل الممكن.
5. المانع يقع على المسار الحرج المتبقي.
6. لا يمكن إنتاج دليل الإغلاق المطلوب دون ذلك العامل الخارجي.

أمثلة:

- secret/credential غير متوفر.
- external provider unavailable.
- required device/environment غير متاح.
- missing GitHub/cloud/production authority.
- unresolved product/business decision لا يمكن استنتاجه قانونيًا.
- destructive operation يحتاج تفويضًا صريحًا.

وثّق:

```text
rootCause
externalOwner
attemptedActions
evidence
whyNotInternallyFixable
affectedUnits
affectedJourneys
completedIndependentWork
minimalUnblockingAction
resumePoint
```

# 34. حالة الحزمة عند Blocked

`BLOCKED_WITH_EXPLICIT_CAUSE` **ليس `CLOSED_WITH_EVIDENCE`**.

لا تشغّل `--closure` متوقعًا نجاحه مع مانع قائم.

لا تزور حالة `DONE/PASS`.

احتفظ بالوحدة المتبقية في حالة غير مغلقة متوافقة مع الإطار، وسجّل المانع في نتائجها/التقرير، وحافظ على Manifest في حالة عدم إغلاق صادقة.

يمكن إعادة `--strict` بعد إعادة الوحدات غير المنجزة إلى حالة التخطيط المناسبة إذا احتاج الأمر للتحقق من سلامة الحزمة، لكن لا تعتبر نجاح `--strict` إغلاقًا تشغيليًا.

# 38. جولة الإغلاق العدائية المستقلة

بعد اعتقادك أن التنفيذ اكتمل:

لا تغلق فورًا.

ابدأ جولة مستقلة جديدة وكأنك مراجع لم يرَ التنفيذ السابق.

حاول اكتشاف:

- root cause لم يُعالج.
- parallel truth.
- stale contract.
- legacy route.
- stale consumer.
- missing migration.
- hidden writer.
- hidden reader.
- journey gap.
- unmapped surface.
- UI control without real effect.
- security bypass.
- stale evidence.
- missing negative test.
- recovery gap.
- runtime-only defect.
- observability gap.

حاول **كسر الإصلاح**.

إذا وجدت خللًا داخليًا:

```text
DO NOT CLOSE
→ REOPEN
→ DIAGNOSE
→ FIX
→ VERIFY
→ REPEAT CLOSURE REVIEW
```

# 39. معايير `CLOSED_WITH_EVIDENCE`

لا تستخدم القرار إلا إذا ثبت:

- root causes removed.
- required foundation closed.
- all in-scope units closed.
- no relevant parallel truth.
- canonical ownership consistent.
- contracts/clients aligned.
- migrations/data integrity verified.
- all relevant writers/readers migrated.
- relevant journeys closed.
- all consuming surfaces read correctly.
- relevant controls have real effects.
- negative/security paths pass.
- retry/recovery paths pass where applicable.
- required runtime evidence exists.
- persisted readback proven.
- required guards pass.
- no stale evidence.
- zero unresolved blockers.
- zero unresolved deviations.
- no internal fixable related defect.
- unrelated work not damaged.

# 40. Package Closure

عند استخدام حزمة، يجب أن تكون جميع الوحدات المنطبقة:

```text
EXECUTION-ORDER status = DONE
EXECUTION status       = DONE

RESULT:
status     = DONE
decision   = PASS
blockers   = []
deviations = []
resultingSha = valid 40-character SHA
```

و:

```text
MANIFEST.status.implementation = COMPLETE
MANIFEST.status.verification   = COMPLETE
MANIFEST.status.decision       = CLOSED_WITH_EVIDENCE
```

أكمل `CLOSURE.md`.

ثم:

```powershell
node tools/diagnose-implementing/validate-package.mjs `
  <PACKAGE_PATH> `
  --strict `
  --closure
```

لا تتوقف حتى تصبح:

```text
Validation summary: 0 error(s)
```

إذا كان هناك مانع خارجي حقيقي، فلا تزور هذه النتيجة؛ استخدم مسار `BLOCKED_WITH_EXPLICIT_CAUSE`.

لا تستخدم:

```text
--disposal
```

ولا تحذف الحزمة تلقائيًا.

# 42. القرار النهائي

القرار يكون واحدًا فقط:

```text
CLOSED_WITH_EVIDENCE
```

عندما تم الإغلاق فعلًا.

أو، فقط كاستثناء نهائي:

```text
BLOCKED_WITH_EXPLICIT_CAUSE
```

بعد استنفاد كل إصلاح داخلي آمن وتنفيذ كل العمل المستقل الممكن.

المبدأ الأخير:

```text
لا تتوقف عند المشكلة.

حوّل المشكلة إلى دليل،
والدليل إلى سبب جذري،
والسبب الجذري إلى إصلاح عند مالك الحقيقة،
والإصلاح إلى تحقق،
والتحقق إلى محاولة كسر،
وأعد الدورة حتى لا تبقى فجوة داخلية مرتبطة
قابلة للإثبات أو المعالجة.
```

الصياغتان لا تفرضان صحة `smsm-dsh-wlt-journeys` ولا أي تقرير مشتق، ولا تضيفان مخطط JSON موازيًا، وتبقيان الإغلاق النهائي متوافقًا مع الفاحص الحالي الذي لا يقبل `--closure` إلا مع كل الوحدات `DONE` والفحوص المطلوبة `PASS` وعدم وجود blockers أو deviations.

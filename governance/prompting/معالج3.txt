تم تثبيت الصياغة على الإطار الريموت الحالي عند رأس فرع `abbas` ‏`e739bbc23ebde37b93f2347bf4c287146d7c9081`. المولد الحالي يتطلب `--surface` حتى للهدف غير السطحي، والفاحص يدعم `--strict` و`--strict --closure` فقط. كما أن مخطط الحزمة الحالي يعتمد الحقول القائمة في القوالب؛ لذلك لا تفرض الصياغة النهائية حقول JSON جديدة قد تسبب تشتتًا أو انحرافًا عن الإطار.   

أُدمجت جميع النقاط الصحيحة الواردة في النسخ السابقة، مع إزالة التكرار والتناقض، وتحويل خط الأساس إلى بوابة إلزامية قبل الرحلات، وترتيب التنفيذ إلى رسم اعتماديات محسوب يمنع إعادة العمل. 

## الأمر الأول: إعداد حزمة التشخيص وخط الأساس وخطة التنفيذ

# الأمر النهائي الحاكم لإعداد حزمة تشخيص وخط أساس وخطة تنفيذ مكتفية ذاتيًا

## مدخلات المهمة

```text
المستودع: <OWNER/REPOSITORY>
الفرع أو المرجع: <BRANCH_OR_REF>
اسم الحزمة: <TASK_NAME>
نوع نقطة البداية:
<JOURNEY | APPLICATION | SURFACE | SECTION | PAGE | FEATURE | FILE | SERVICE | DOMAIN | OTHER>
نقطة البداية: <TARGET>
النتيجة التشغيلية المطلوبة: <MEASURABLE_OBJECTIVE>
تفويض تسليم الحزمة: <NO_COMMIT | COMMIT | COMMIT_AND_PUSH>
```

نفّذ عبر GitHub Remote مرحلة **التشخيص والتخطيط وإعداد الحزمة فقط** على الفرع أو المرجع المحدد، ولا تنفذ خلال هذه المرحلة أي تعديل تشغيلي في كود المنتج.

ابدأ بجلب أحدث رأس ريموت للمرجع المحدد وتثبيت `SHA` كامل بطول أربعين حرفًا بوصفه المصدر الوحيد للحالة التي ستُشخّص وتُبنى عليها الحزمة. لا تعتمد على الذاكرة أو حالة محلية أو تقرير أو حزمة أو محادثة سابقة لإثبات واقع المستودع.

يُمنع خلال هذه المرحلة تعديل أو حذف أو نقل أو إعادة تسمية أي ملف تشغيلي أو تطبيقي أو عقد أو قاعدة بيانات أو هجرة أو اختبار أو إعداد Runtime أو حوكمة خارج مجلد الحزمة.

---

## 1. إنشاء الحزمة من الإطار القائم

أنشئ الحزمة حصريًا داخل:

```text
tools/diagnose-implementing/<TASK_NAME>/
```

واستخدم فقط الإطار الموجود فعليًا في المرجع المثبت:

```text
tools/diagnose-implementing/_template/
tools/diagnose-implementing/new-package.mjs
tools/diagnose-implementing/new-unit.mjs
tools/diagnose-implementing/validate-package.mjs
```

يُمنع إنشاء بنية موازية أو إعادة استخدام هياكل قديمة مثل:

```text
topics/
contexts/
journeys/
```

استخدم المولد الحالي:

```powershell
node tools/diagnose-implementing/new-package.mjs `
  --name <TASK_NAME> `
  --branch <BRANCH_OR_REF> `
  --sha <PINNED_REMOTE_SHA> `
  --surface "<TARGET>" `
  --objective "<TARGET_KIND>: <MEASURABLE_OBJECTIVE>" `
  --repository <OWNER/REPOSITORY>
```

الخيار `--surface` هو اسم مدخل المولد الحالي، ولا يعني أن الهدف يجب أن يكون سطحًا. وثّق النوع الحقيقي للهدف واسم نقطة البداية والنتيجة المطلوبة داخل `MANIFEST.json` و`GLOBAL-DIAGNOSIS.md` و`COVERAGE.json`.

لا تغيّر `schemaVersion`، ولا تستبدل القوالب، ولا تضف بنية أو مصدر حقيقة موازٍ للإطار الحالي.

## 2. ترتيب السلطة ومصادر الحقيقة

قبل التشخيص التفصيلي:

1. اقرأ `AGENTS.md`.
2. اقرأ ترتيب السلطة والحوكمة الفعالة المشار إليها من المستودع.
3. اقرأ ملفات البروتوكول والحوكمة والعقود والسجلات الحاكمة المرتبطة بالمهمة.
4. حدّد الترتيب القانوني لمصادر الحقيقة عند التعارض.
5. لا تسمح لملفات الحزمة أن تتجاوز:
   - الكود الحي.
   - قاعدة البيانات.
   - العقود المركزية.
   - الحوكمة الفعالة.
   - الخدمة المالكة للمجال.
6. لا تنشئ سياسة أو معمارية جديدة داخل الحزمة.
7. لا تعيد تصميم الحل إلا إذا أثبت التشخيص وجود خلل معماري، وعندها خطط للتصحيح وفق السلطة القائمة.

أنشئ قائمة تغطية حوكمية داخل `GLOBAL-DIAGNOSIS.md` تربط كل ملف حوكمة أو بروتوكول منطبق بما يلي:

```text
المصدر
سبب الانطباق
الأجزاء المؤثرة
Coverage IDs المرتبطة
Unit IDs المرتبطة
خطوة التنفيذ أو سبب الاستبعاد
الدليل
أمر التحقق
أثر إسقاطه
```

يُمنع استبعاد بند بعبارات عامة مثل:

```text
حسب الحاجة
عند اللزوم
لاحقًا
غير مهم
غير مؤثر
خارج النطاق
```

دون دليل وسبب قابل للتحقق.

## 3. الفصل بين نطاق التشخيص ونطاق التنفيذ

طبّق الفصل التالي بدقة:

```text
نطاق التشخيص:
المستودع كله، بالقدر اللازم لاكتشاف الروابط والفجوات الخفية
ومصادر الحقيقة والاعتماديات والرحلات العابرة للأسطح.

نطاق التنفيذ المخطط:
نقطة البداية وكل عنصر يثبت ارتباطه بها مباشرة أو انتقاليًا،
وكل أساس مشترك يجب استقراره قبل تنفيذها.
```

لا تحول كل عيب مكتشف في المستودع إلى وحدة تنفيذ.

يُعد العنصر داخل نطاق التنفيذ إذا ثبت أنه:

- يملك الحقيقة أو السياسة أو العقد أو سلطة الكتابة.
- يكتب الحالة أو يقرأها أو يشتق منها قرارًا.
- يبدأ التدفق أو يكمله أو يعتمد على نتيجته.
- يسبق الرحلة أو يتبعها أو يتأثر بنجاحها أو فشلها.
- يديرها أو يعرضها في سطح أو قسم آخر.
- يستهلك العقد أو العميل أو الخدمة أو الجدول أو الحدث نفسه.
- يعتمد على الهوية أو الصلاحية أو التكليف أو النطاق الموثوق نفسه.
- يحمل أثرًا تشغيليًا أو ماليًا أو أمنيًا أو تدقيقيًا.
- يحتوي نسخة قديمة أو محلية أو مكررة أو موازية من الحقيقة.
- يلزم تغييره أو اختباره لإثبات الإغلاق الكامل.

صنّف العيب غير المرتبط:

```text
DEFECT_OUTSIDE_EXECUTION_SCOPE
```

وسجّل:

```text
الدليل
سبب الاستبعاد
أثر عدم المعالجة
المالك المقترح
شرط إعادة الفتح
```

ولا تنشئ له وحدة تنفيذ في الحزمة الحالية.

صنّف الاعتماد الخارجي:

```text
EXTERNAL_DEPENDENCY
```

مع الدليل والمالك وشرط إعادة الفتح، ولا تستخدمه لإخفاء خلل داخلي قابل للمعالجة.

## 4. التغطية الإلزامية

استكمل جميع العناصر المولدة في `COVERAGE.json`، ولا تترك أي عنصر:

```text
UNASSESSED
```

افحص على الأقل:

- المستودع بوصفه وحدة كاملة.
- `control-panel`.
- `app-client`.
- `app-partner`.
- `app-captain`.
- `app-field`.
- كل سطح أو بوابة أخرى مكتشفة.
- جميع أقسام لوحة التحكم ومساراتها الحالية.
- المسارات الديناميكية أو غير الظاهرة في القائمة الرئيسية.
- الواجهات المشتركة.
- الخلفيات والخدمات.
- قواعد البيانات والهجرات.
- العقود والعملاء المولدين.
- الأحداث والمهام والطوابير والتكاملات.
- الهوية والجلسات والصلاحيات والتكليفات.
- الأمن والنطاقات الموثوقة.
- Docker وRuntime والبيئة والمنافذ.
- الصحة والجاهزية والمراقبة والتدقيق.
- الاختبارات والبناء والحراس وCI.
- الأدوات والحوكمة والملكية.
- الملفات القديمة والمكررة والمهجورة والاحتياطية.
- المسارات الحية البديلة ومصادر الحقيقة الموازية.

لكل عنصر مرتبط استخدم:

```text
assessment: RELATED
executionDisposition: IN_SCOPE
evidenceRefs: غير فارغة
unitIds: غير فارغة
summary: نتيجة واضحة
```

ولكل عنصر مستبعد أو خارج النطاق، أضف الدليل وسبب الاستبعاد وشرط إعادة الفتح.

ابقِ التغطية مضغوطة على مستوى المستودع أو المجال أو السطح أو القسم إذا ثبت عدم الارتباط وعدم وجود عيب مادي.

توسع إلى مستوى:

```text
المسار
الملف
الرمز
الصفحة
التبويب
التحكم
الحالة
القارئ
الكاتب
العقد
الرحلة
```

عندما يكون العنصر مرتبطًا بالتنفيذ أو يحتوي فجوة مؤثرة.

لا تنشئ آلاف السجلات الشكلية، ولا تستخدم غياب السجل بوصفه دليل استبعاد.

## 5. مرحلة خط الأساس الإلزامية

يجب أن تبدأ خطة التنفيذ بمرحلة مستقلة:

```text
PHASE-00 — BASELINE_STABILIZATION
```

هذه المرحلة ليست رحلة تشغيلية. هدفها كشف ومعالجة الفجوات الأساسية المشتركة أو العابرة للأسطح قبل بدء الرحلات، لمنع تكرار الإصلاحات أو بناء الرحلات فوق أساس غير مستقر.

افحص داخل خط الأساس:

1. ترتيب السلطة والحوكمة.
2. ملكية المجالات ومصادر الحقيقة.
3. سلطة الكتابة والقراءة.
4. الهوية والجلسات والأجهزة.
5. الأدوار والصلاحيات والتكليفات.
6. النطاقات الموثوقة.
7. قواعد البيانات والمخططات والهجرات.
8. القيود والفهارس والمعاملات.
9. العقود المركزية.
10. العملاء المولدين ومصدر توليدهم.
11. توافق الطلبات والاستجابات والأخطاء والحالات.
12. حدود الخدمات واتجاهات الاعتماديات.
13. آلات الحالات والسياسات المشتركة.
14. Shared frontend brains.
15. الكتاب والقراء والمستهلكين عبر الأسطح.
16. الأحداث والمهام والطوابير و`Outbox/Inbox`.
17. التكرار و`Idempotency` والسباقات والتعويض.
18. Runtime وDocker والمنافذ والبيئة.
19. الصحة والجاهزية والمراقبة والتدقيق.
20. الحراس والاختبارات والبناء.
21. الملفات المكررة أو المهجورة.
22. مصادر الحقيقة والعقود والمسارات الموازية.

صنّف كل فجوة مرتبطة إلى أحد التصنيفات التالية داخل التشخيص:

```text
FOUNDATION_BLOCKER
SHARED_PREREQUISITE
JOURNEY_PREREQUISITE
JOURNEY_LOCAL
SHARED_OPTIMIZATION
NON_BLOCKING_DEBT
EXTERNAL_DEPENDENCY
```

طبّق القواعد التالية:

- الخلل الذي يؤثر في رحلتين أو أكثر، أو سطحين أو أكثر، أو مصدر مركزي، يُعالج في وحدة `FOUNDATION` أو `MIGRATION` مشتركة.
- يُمنع تكرار الإصلاح المشترك داخل كل رحلة.
- الخلل الذي يمنع رحلة واحدة فقط يُسجل متطلبًا سابقًا لها.
- الخلل المحصور داخل الرحلة يبقى في وحدتها.
- الدين غير المانع لا يعطل الرحلات، لكنه يُسجل مع مالكه وأثره.
- المانع الخارجي لا يتحول إلى نجاح أو إلى عذر لتجاوز خلل داخلي.

## 6. وحدات خط الأساس وبوابته

أنشئ وحدة واحدة فقط لكل شأن تأسيسي مستقل وغير متداخل، باستخدام النوع المناسب:

```text
FOUNDATION
MIGRATION
```

استخدم:

```powershell
node tools/diagnose-implementing/new-unit.mjs `
  tools/diagnose-implementing/<TASK_NAME> `
  --id <UNIT_ID> `
  --name <UNIT_NAME> `
  --kind <FOUNDATION_OR_MIGRATION> `
  --depends-on "<DEPENDENCY_IDS>"
```

بعد وحدات الأساس، أنشئ وحدة واحدة من نوع:

```text
VERIFICATION
```

تكون بوابة إغلاق خط الأساس، وتعتمد على جميع وحدات الأساس المنطبقة.

إذا لم تظهر فجوات تأسيسية، لا تلغِ البوابة؛ أنشئ وحدة تحقق تثبت أن الأساس صالح للرحلات بالأدلة والفحوص.

يجب أن تعتمد كل وحدة رحلة مباشرة أو انتقاليًا على بوابة إغلاق خط الأساس.

يُمنع وجود وحدة `JOURNEY` مستقلة عن بوابة الأساس.

لا تعتبر خط الأساس مخططًا للإغلاق إلا إذا كانت الخطة قادرة على إثبات عدم وجود:

```text
مانع تأسيسي غير معالج
مصدر حقيقة موازٍ
كاتب بلا مالك واضح
مسار صلاحية غير موثوق
عقد مركزي مكسور
عميل مولد من مصدر خاطئ أو منجرف
هجرة غير متحققة
تناقض حالة عابر للأسطح
اعتماد مخالف للحدود
فشل Runtime تأسيسي
اعتماد تأسيسي غير مخطط
فجوة تأسيسية بلا وحدة
وحدة تأسيسية بلا فحص
```

خطط لتشغيل:

```powershell
pnpm run guard:foundation
```

في التنفيذ:

- لتسجيل الوضع الأولي.
- بعد تنفيذ وحدات الأساس.
- قبل بدء أول رحلة.
- بعد أي تغيير لاحق يمس الأساس.
- قبل الإغلاق النهائي.

## 7. اكتشاف الرحلات وتسلسلها

استخرج الرحلات من مصدرين مستقلين:

1. السجلات والحوكمة والخطط والوثائق الفعالة.
2. الكود والعقود والبيانات والواجهات وRuntime الفعلي.

قارن المصدرين، واكتشف:

- الرحلات الموثقة وغير الموثقة.
- الصريحة والضمنية.
- الكاملة والمجزأة.
- السابقة واللاحقة.
- الداخلة والخارجة.
- المتداخلة أو المكررة.
- المتناقضة.
- المغلقة شكليًا بلا دليل.
- الموجودة في السجل دون تنفيذ.
- الموجودة في الكود دون تسجيل.

لكل رحلة مرتبطة، وثّق في `GLOBAL-DIAGNOSIS.md` أو `DIAGNOSIS.md`:

## 9. إنشاء وحدات التنفيذ

أنشئ وحدة واحدة لكل شأن تنفيذي مستقل وغير متداخل باستخدام الأنواع المدعومة حاليًا:

```text
TOPIC
CONTEXT
JOURNEY
FOUNDATION
MIGRATION
CLEANUP
VERIFICATION
```

استخدم:

```powershell
node tools/diagnose-implementing/new-unit.mjs `
  tools/diagnose-implementing/<TASK_NAME> `
  --id <UNIT_ID> `
  --name <UNIT_NAME> `
  --kind <UNIT_KIND> `
  --depends-on "<DEPENDENCY_IDS>"
```

لا تنشئ الوحدة يدويًا.

يمكن للوحدة الواحدة أن ترتبط بعدة موضوعات وسياقات ورحلات وأسطح إذا كان شأن التنفيذ ومالك الحقيقة واحدًا.

إذا احتاجت عدة رحلات تعديل العقد أو المخطط أو الخدمة أو Shared Brain أو مصدر الحقيقة نفسه، اجمع التغيير في وحدة مشتركة واحدة، ثم اجعل الرحلات تعتمد عليها.

يُمنع:

- تكرار الإصلاح نفسه في عدة وحدات.
- تقسيم المشكلة حسب الأسطح إذا كان مالكها واحدًا.
- خلط مشكلات مستقلة في وحدة ضخمة.
- إنشاء وحدة بلا دليل ارتباط.
- ترك ارتباط مثبت بلا وحدة.
- تكرار `executionConcern`.
- إنشاء دورة اعتماد.
- استخدام اعتماد غير موجود.

## 10. المحتوى الإلزامي للوحدات

### `DIAGNOSIS.md`

يجب أن يشرح:

- الواقع الحالي.
- الأدلة الدقيقة.
- السبب الجذري.
- مالك الحقيقة الصحيح.
- الكتاب والقراء والمستهلكين.
- الرحلات والأسطح المتأثرة.
- أثر الفجوة.
- سبب تصنيف الوحدة.
- الاعتماديات.
- ما يجب تنفيذه قبلها.
- ما ستفتحه بعد تنفيذها.
- الحدود.
- ما لا يجوز تغييره.
- سبب موضعها في ترتيب التنفيذ.
- أثر تأخيرها أو تقديمها.

يجب أن يكون التشخيص عميقًا ومحددًا، لا عنوانًا أو ملخصًا عامًا.

### `EXECUTION.json`

حافظ على المخطط الحالي، واستكمل الحقول القائمة:

```text
schemaVersion
unitId
name
kind
status
executionConcern
objective
truthOwner
coverageIds
topics
contexts
journeys
affectedSurfaces
dependsOn
tasks
```

يجب أن يكون:

```text
executionConcern
```

محددًا وفريدًا وغير متداخل مع أي وحدة أخرى.

يجب أن تحدد كل مهمة:

```text
taskId
order
objective
paths
symbols
action
currentProblem
requiredChange
targetState
mustNotChange
acceptanceCriteria
verificationIds
rollback
commitBoundary
```

يجب أن يطابق `taskId` النمط:

```text
<UNIT_ID>-T001
<UNIT_ID>-T002
...
```

ويجب أن تكون أوامر التنفيذ ذرية ودقيقة.

يُمنع استخدام تعليمات عامة مثل:

```text
أصلح المشكلة
راجع الكود
حسّن التنفيذ
أكمل الرحلة
اربط الأسطح
نظف الملفات
```

دون تحديد:

- المسارات.
- الرموز.
- المشكلة الحالية.
- التغيير المطلوب.
- الحالة النهائية.
- المحظورات.
- معايير القبول.
- الفحوص.
- التراجع.
- حد Commit.

### `VERIFICATION.json`

حافظ على المخطط الحالي، وأنشئ `checks` تتضمن لكل فحص:

```text
verificationId
type
command
required
prerequisites
passCriteria
failCriteria
proves
doesNotProve
```

يجب أن تكون جميع `verificationIds` المشار إليها في المهام موجودة فعليًا.

لا تجعل نجاح فحص واحد يثبت أكثر مما يثبت فعليًا.

## 11. الترتيب التنفيذي الذكي

أنشئ رسم اعتماديات موجّهًا وخاليًا من الدورات باستخدام `dependsOn`.

استخدم ترتيب الوحدات داخل `EXECUTION-ORDER.json` ليعكس ترتيب التنفيذ المختار، ووثّق سبب الترتيب والمسار الحرج وحسابات الأولوية في `GLOBAL-DIAGNOSIS.md` وتشخيص الوحدات، دون تغيير `schemaVersion` أو اختراع مصدر حقيقة منفصل.

طبّق القواعد التالية:

1. لا تبدأ وحدة قبل اكتمال جميع اعتمادياتها.
2. نفّذ جميع موانع خط الأساس قبل الرحلات.
3. حدّد المسار الحرج من خط الأساس إلى الإغلاق.
4. قدّم الوحدة الموجودة على المسار الحرج.
5. قدّم الوحدة التي تفتح أكبر عدد من الرحلات.
6. ثم الوحدة التي تفتح أكبر عدد من الأسطح.
7. ثم الوحدة التي تعالج مصدرًا مركزيًا وتمنع تكرار العمل.
8. نفّذ التغييرات عالية المخاطر أو عالية عدم اليقين مبكرًا.
9. قدّم الإصلاح الصغير واسع الأثر.
10. قلّل إعادة فتح الملفات والعقود والمخططات نفسها.
11. اجمع تغييرات العقد وتوليد العملاء في نقطة واحدة.
12. اجعل التنظيف غير المانع والديون غير الحرجة في النهاية.

عند تساوي الوحدات الجاهزة، اختر وفق:

```text
المسار الحرج
→ عدد الرحلات المفتوحة
→ عدد الأسطح المفتوحة
→ اتساع أثر مالك الحقيقة
→ مقدار منع إعادة العمل
→ المخاطر الأعلى أولًا
→ الجهد الأقل مع الأثر الأعلى
→ تكلفة التحقق الأقل
```

وثّق لكل وحدة:

```text
سبب الترتيب
ما الذي تمنعه
ما الذي تفتحه
أثر تأخيرها
خطر تنفيذها
خطر عدم تنفيذها
```

لا تستخدم رقم الوحدة وحده بوصفه سبب الترتيب.

## 12. سياسة السرعة والتوازي

خطط للتوازي الآمن في:

- القراءة والجرد.
- البحث عن الاستخدامات.
- تحليل العلاقات.
- مراجعة العقود.
- جمع الأدلة.
- الفحوص الساكنة المستقلة.
- اختبارات الحزم غير المتعارضة.

يجب أن يبقى متسلسلًا:

- تعديل الكود داخل الوحدة الحالية.
- تعديل مصدر حقيقة مشترك.
- الهجرات وBackfill.
- تغيير العقود المركزية.
- توليد العملاء.
- تعديل ملفات أو مخططات مشتركة.
- Commit.
- تحديث حالات الوحدة والحزمة.

لا تخطط لأكثر من وحدة كتابة واحدة في حالة `IN_PROGRESS`.

## 13. استراتيجية التحقق

خطط للفحوص بهذا التدرج:

```text
فحص الملف أو الرمز المتأثر
→ اختبار الوحدة أو الحزمة
→ اختبار التكامل المرتبط
→ affected lint/typecheck/test/build
→ الحراس المنطبقة
→ الفحوص الشاملة عند نقاط التثبيت
→ Runtime/Smoke/E2E عند اكتمال الشريحة الرأسية
```

يجب أن تغطي الفحوص المنطبقة:

- التنسيق وLint.
- التحليل الساكن.
- Type checking.
- Unit tests.
- Integration tests.
- العقود والعملاء المولدين.
- الهجرات والتراجع وسلامة البيانات.
- الصلاحيات والاختبارات السلبية.
- الأمن.
- بناء الحزم والأسطح المتأثرة.
- الصحة والجاهزية.
- Smoke.
- E2E العابر للأسطح.
- قبول UI وUX.
- القراءة الراجعة من البيانات المحفوظة.
- المراقبة والتدقيق.

لا تخطط لتشغيل كل المستودع بعد كل تعديل صغير، ولا تؤجل كل الفحوص الشاملة إلى النهاية.

خطط لنقاط التثبيت:

```text
CHECKPOINT-0:
SHA البداية والتشخيص الأولي.

CHECKPOINT-1:
إغلاق خط الأساس.

CHECKPOINT-2:
استقرار البيانات والهجرات والعقود والعملاء.

CHECKPOINT-3:
استقرار الخدمات وآلات الحالات.

CHECKPOINT-4:
اكتمال ربط الأسطح وتجربة المستخدم.

CHECKPOINT-5:
نجاح Runtime وSmoke وE2E والقراءة الراجعة.
```

وثّق نقاط التثبيت وخطة التراجع داخل ملفات التشخيص والتحقق الحالية، دون إنشاء مخطط موازٍ غير مطلوب.

## 14. إبطال الأدلة وإعادة فتح خط الأساس

خطط لاعتبار الأدلة السابقة غير صالحة إذا تغير بعد نجاحها:

- مصدر حقيقة.
- عقد مركزي.
- عميل مولد.
- مخطط أو هجرة.
- هوية أو صلاحية.
- آلة حالة مشتركة.
- Shared Brain.
- إعداد Runtime تأسيسي.

إذا اكتُشفت أثناء تنفيذ رحلة فجوة تأسيسية جديدة، يجب أن تنص الخطة على:

1. إيقاف الرحلة عند حد آمن.
2. تسجيل الدليل.
3. تصنيف الفجوة.
4. إعادة فتح وحدة الأساس المالكة أو إنشاء وحدة مستقلة.
5. إعادة الوحدات المتأثرة إلى `READY` عند الحاجة.
6. إبطال نتائج الفحوص التي سبقت تغيير الأساس.
7. معالجة خط الأساس.
8. إعادة فحوصه.
9. إعادة حساب المسار الحرج.
10. إعادة فحوص الرحلات المتأثرة.
11. استكمال التنفيذ.

يُمنع ترقيع خلل مشترك داخل رحلة واحدة فقط.

## 15. PostgreSQL عند الانطباق

كل تغيير مخطط لـPostgreSQL يجب أن يحدد:

- ملف هجرة SQL متسلسل وحتمي.
- المعاملة عند دعم العملية لها.
- التوافق أثناء الانتقال.
- Backfill أو تحويل البيانات.
- القيود والفهارس.
- ترتيب نقل القراء والكتّاب.
- اختبار الهجرة على PostgreSQL فعلي.
- اختبار الثوابت وسلامة البيانات.
- اختبار التراجع أو خطة التعويض.
- إزالة المصدر القديم بعد نقل جميع المستهلكين.

لا تخطط لتعديل مخطط حي يدويًا خارج الهجرات.

تبقى قاعدة البيانات مصدر حقيقة الحالة المخزنة، وتبقى الخدمة المالكة سلطة منطق المجال والكتابة.

لا تقبل معرفات أو نطاقات يرسلها العميل بوصفها دليل صلاحية دون مطابقتها مع الهوية والسياق الموثوقين.

## 16. جاهزية الحزمة

بعد اكتمال التشخيص والخطة:

1. حدّث `MANIFEST.json`:
   - `diagnosis: COMPLETE`
   - `plan: READY`
2. حدّث `COVERAGE.json`:
   - `assessmentStatus: COMPLETE`
3. حدّث `EXECUTION-ORDER.json`:
   - `status: READY`
4. اجعل جميع الوحدات:
   - `READY`
   - أو `DONE` فقط إذا كانت مكتملة سابقًا بأدلة صالحة.
5. وحّد حالة كل وحدة بين:
   - `EXECUTION-ORDER.json`
   - `EXECUTION.json`
6. تأكد من:
   - عدم وجود `UNASSESSED`.
   - عدم وجود اعتماد مفقود.
   - عدم وجود دورة اعتماد.
   - عدم وجود `executionConcern` مكرر.
   - عدم وجود مهمة غامضة.
   - عدم وجود فحص مشار إليه وغير موجود.
   - ارتباط التغطية بالوحدات في الاتجاهين.
   - اعتماد كل رحلة على بوابة خط الأساس.
   - عدم وجود علامات قالب أو أسرار أو بيانات حساسة.

شغّل:

```powershell
node tools/diagnose-implementing/validate-package.mjs `
  tools/diagnose-implementing/<TASK_NAME> `
  --strict
```

عالج جميع الأخطاء حتى تكون النتيجة:

```text
Validation summary: 0 error(s)
```

لا تستخدم:

```text
--disposal
```

لأنه ليس وضعًا مدعومًا.

## الأمر الثاني: تنفيذ الحزمة أو المهمة المباشرة

# الأمر النهائي الحاكم لتنفيذ الحزمة أو المهمة المباشرة من خط الأساس حتى الإغلاق المثبت

## مدخلات التنفيذ

```text
المستودع: <OWNER/REPOSITORY>
الفرع أو المرجع: <BRANCH_OR_REF>
مسار الحزمة عند وجودها: <PACKAGE_PATH | NONE>
المهمة المباشرة عند عدم وجود حزمة: <DIRECT_TASK | NONE>
التفويض: <LOCAL_ONLY | COMMIT | COMMIT_AND_PUSH>
```

نفّذ المهمة فعليًا داخل المستودع من أسبابها الجذرية حتى الإغلاق المثبت، مع المحافظة على الحوكمة الحية ومعمارية الفول ستاك الموحد متعدد الأسطح وحدود الملكية ومصادر الحقيقة والعقود.

لا تستخدم نجاح البناء وحده أو كثرة التعديلات أو ظهور الواجهة بوصفها دليل اكتمال.

---

## 1. تحديد وضع التنفيذ

### عند توفير حزمة

اعتبر الحزمة خطة دعم مشتقة وليست مصدر حقيقة أعلى من المستودع.

اقرأها بهذا الترتيب:

```text
START-HERE.md
→ MANIFEST.json
→ GLOBAL-DIAGNOSIS.md
→ COVERAGE.json
→ EXECUTION-ORDER.json
→ الوحدة الحالية/DIAGNOSIS.md
→ الوحدة الحالية/EXECUTION.json
→ الوحدة الحالية/VERIFICATION.json
→ الوحدة الحالية/RESULT.json
```

شغّل:

```powershell
node tools/diagnose-implementing/validate-package.mjs `
  <PACKAGE_PATH> `
  --strict
```

لا تبدأ تعديل الكود إذا فشل الفحص الصارم. صحح تناقضات الحزمة أولًا، ولا تخفف الهدف أو معايير القبول لإجبارها على النجاح.

### عند عدم توفير حزمة

نفّذ تشخيصًا مستهدفًا يحدد:

- السبب الجذري.
- مالك الحقيقة.
- الملفات والرموز.
- الكتاب والقراء والمستهلكين.
- الأسطح والرحلات الداخلة والخارجة.
- المتطلبات التأسيسية.
- الفحوص اللازمة.

يمكن تنفيذ المهمة مباشرة فقط إذا كانت محدودة وواضحة ولا تتطلب أكثر من شأن جذري مستقل ولا تعبر عدة مجالات أو أسطح بصورة تجعل التنفيذ دون حزمة عالي المخاطر.

إذا اتضح أن المهمة واسعة أو متعددة المجالات أو متعددة الأسطح أو تحتاج خط أساس مشتركًا، أنشئ حزمة بالأمر الأول ثم نفّذها، بدل الاستمرار في تعديلات غير مخططة.

---

## 2. تثبيت الحالة وحماية المستودع

قبل أي تعديل:

1. اجلب أحدث حالة ريموت للمرجع المحدد.
2. ثبّت `STARTING_REMOTE_SHA`.
3. افحص شجرة العمل.
4. افحص الاختلافات المحلية.
5. حدّد التغييرات السابقة غير المرتبطة بالمهمة.
6. لا تحذفها أو تعكسها أو تستبدلها.
7. افصل تغييرات المهمة عنها.
8. اقرأ الحوكمة وترتيب السلطة والعقود الفعالة.
9. تحقق من أن المرجع المطلوب هو المرجع الجاري العمل عليه.

يُمنع دون تفويض صريح:

```text
git reset --hard
git clean
force push
إعادة كتابة التاريخ
حذف تغييرات غير مرتبطة
الدمج إلى فرع آخر
إنشاء Release
تغيير Production
```

سجل في بداية التنفيذ:

```text
starting remote SHA
working tree state
package pinned SHA عند وجودها
latest observed remote SHA
```

---

## 3. معالجة انحراف الفرع عن الحزمة

عند وجود حزمة، قارن:

```text
pinnedStartSha
latestObservedRemoteSha
current remote head
```

إذا تحرك الفرع منذ إعداد الحزمة:

1. افحص الفرق من `pinnedStartSha` إلى الرأس الحالي.
2. حدّد أثره على:
   - الملفات.
   - الرموز.
   - العقود.
   - العملاء.
   - المخططات.
   - الملكيات.
   - الاعتماديات.
   - الرحلات.
   - الوحدات.
   - الفحوص.
3. حدّث الأدلة والتغطية والوحدات المتأثرة فقط.
4. حدّث `latestObservedRemoteSha`.
5. أعد حساب ترتيب الاعتماديات والمسار الحرج.
6. أعد تشغيل `--strict`.
7. لا تعِد تشخيص المستودع كاملًا إلا إذا أثبت الفرق تغيرًا جوهريًا في الملكية أو المعمارية أو النطاق.

لا توسع أو تقلص النطاق بصمت.

كل ارتباط جديد يثبت أثناء التنفيذ يجب أن:

- يُسجل في `COVERAGE.json`.
- يرتبط بوحدة قائمة أو وحدة جديدة غير متداخلة.
- يُضاف إلى ترتيب الاعتماديات.
- يخضع للفحص الصارم قبل الاستمرار.

---

## 4. بوابة خط الأساس قبل الرحلات

عند تنفيذ حزمة تحتوي رحلة أو تطبيقًا أو سطحًا أو تدفقًا عابرًا للأسطح، يُمنع بدء أي وحدة من نوع:

```text
JOURNEY
TOPIC مرتبط برحلة
CONTEXT مرتبط برحلة
```

قبل إغلاق وحدات خط الأساس وبوابة التحقق التابعة لها.

في بداية التنفيذ:

1. شغّل:

```powershell
pnpm run guard:foundation
```

2. سجّل نتيجته الأولية بوصفها دليلًا.
3. لا تعتبر فشله الأولي مخرجًا مبكرًا؛ عالج أسبابه الداخلية داخل وحدات الأساس.
4. نفّذ وحدات:
   - `FOUNDATION`
   - `MIGRATION`
   - المتطلبات المشتركة السابقة للرحلات.
5. نفّذ وحدة التحقق الخاصة بإغلاق خط الأساس.
6. أعد تشغيل `guard:foundation`.
7. شغّل جميع فحوص الأساس الإلزامية.
8. لا تبدأ أول رحلة حتى تنجح البوابة.
9. سجل SHA نتيجة كل وحدة تأسيسية داخل `RESULT.json`.
10. اجعل SHA الناتج عن بوابة الأساس هو قاعدة تنفيذ الرحلات، ووثّقه في نتائج البوابة و`CLOSURE.md`.

إذا لم تحتوي المهمة المباشرة الصغيرة على رحلة أو سطح أو أثر مشترك، لا تُحوّلها إلى معالجة تأسيسية كاملة للمستودع؛ افحص فقط المتطلبات التأسيسية المرتبطة بها.

لا يجوز بدء الرحلات إذا بقي:

```text
FOUNDATION_BLOCKER
SHARED_PREREQUISITE مانع
خلل داخلي قابل للمعالجة في مصدر حقيقة مشترك
فشل إلزامي في بوابة الأساس
```

## 5. شروط إغلاق خط الأساس

لا تغلق بوابة الأساس إلا إذا أثبتت الأدلة والفحوص عدم وجود:

```text
مانع تأسيسي غير معالج
مصدر حقيقة موازٍ
كاتب بلا مالك واضح
نطاق صلاحية غير موثوق
عقد مركزي مكسور
عميل مولد منجرف أو مجهول المصدر
هجرة غير متحققة
تناقض حالة عابر للأسطح
اعتماد مخالف لحدود المجالات
فشل Runtime تأسيسي
اعتماد تأسيسي غير مخطط
وحدة أساس بلا فحص
فحص إلزامي فاشل
```

لا تكتب عدادات نجاح يدوية بوصفها دليلًا. استخرج القرار من:

```text
COVERAGE.json

EXECUTION.json
VERIFICATION.json
RESULT.json
الأدلة الفعلية
نتائج الأوامر

```

## 6. المجدول التنفيذي الذكي

بعد إغلاق الأساس، كوّن قائمة الوحدات الجاهزة التي اكتملت جميع اعتمادياتها.

اختر الوحدة التالية وفق هذا الترتيب:

1. الوحدة الواقعة على المسار الحرج.
2. الوحدة التي تفتح أكبر عدد من الرحلات.
3. الوحدة التي تفتح أكبر عدد من الأسطح.
4. الوحدة التي تعالج مصدرًا مركزيًا وتمنع تكرار العمل.
5. الوحدة عالية المخاطر أو عدم اليقين.
6. الإصلاح الصغير واسع الأثر.
7. الوحدة التي تقلل إعادة فتح ملف أو عقد أو مخطط سبق تثبيته.
8. وحدة التنظيف غير المانعة في النهاية.

عند التساوي، استخدم:

```text
المسار الحرج
→ عدد الرحلات المفتوحة
→ عدد الأسطح المفتوحة
→ اتساع أثر مالك الحقيقة
→ مقدار منع إعادة العمل
→ المخاطر الأعلى
→ الجهد الأقل مع الأثر الأعلى
→ تكلفة التحقق الأقل
```

سجّل سبب اختيار الوحدة داخل `RESULT.json` أو تشخيص الوحدة أو تقرير التنفيذ، دون تغيير مخطط الحزمة أو إنشاء مصدر ترتيب موازٍ.

لا تنتقل آليًا حسب رقم الوحدة فقط.

## 7. التوازي الآمن

حافظ على وحدة تعديل واحدة فقط في حالة:

```text
IN_PROGRESS
```

يمكن تنفيذ ما يلي بالتوازي إذا كان مستقلًا:

- القراءة.
- البحث.
- تحليل العلاقات.
- مراجعة العقود.
- جمع الأدلة.
- الفحوص الساكنة.
- اختبارات حزم لا تعتمد على نواتج غير مكتملة.

يُمنع التوازي في:

- تعديل الكود المتعارض.
- تعديل مصدر حقيقة مشترك.
- تغيير العقود المركزية.
- توليد العملاء.
- الهجرات وBackfill.
- تعديل الملفات أو المخططات المشتركة.
- Commit.
- تحديث حالة الوحدة ونتيجتها.

التوازي وسيلة لتسريع القراءة والفحص، وليس لتجاوز ترتيب الاعتماديات أو إنشاء كتابات متعارضة.

## 8. تنفيذ الوحدة

لكل وحدة:

1. تحقق أن المسارات والرموز ما تزال صحيحة.
2. تحقق أن مالك الحقيقة لم يتغير.
3. اقرأ السبب الجذري والحالة المستهدفة.
4. تحقق من اكتمال جميع `dependsOn`.
5. اجعل الوحدة الوحيدة الحالية `IN_PROGRESS`.
6. نفّذ المهام حسب `order`.
7. نفّذ أقل تغيير جذري كامل يحقق الحالة المستهدفة.
8. حدّث جميع الكتاب والقراء والمستهلكين.
9. انقل المستهلكين قبل إزالة المصدر القديم.
10. أزل:
    - الاستيرادات القديمة.
    - العقود الموازية.
    - الإعدادات القديمة.
    - الاختبارات القديمة غير الصحيحة.
    - الوثائق المضللة.
    - المسارات المهجورة.
    - البقايا الميتة.
11. شغّل الفحوص المرتبطة بكل مهمة.
12. لا تنتقل إلى المهمة التالية إذا فشل فحص مانع.
13. سجّل النتائج الفعلية.
14. أنشئ Commit عند حد الوحدة المنطقي إذا سمح التفويض.
15. لا تجعل الوحدة `DONE` قبل نجاح كل فحوصها الإلزامية.

يُمنع:

- الترقيع المؤقت.
- `Fallback` الصامت.
- مصادر الحقيقة الموازية.
- العقود والأنواع اليدوية الموازية.
- تكرار المنطق أو آلات الحالات.
- Mocks أو Fixtures في المسارات الحية.
- الأزرار أو الواجهات الزائفة.
- تعطيل الاختبارات أو تخفيف القيود لإخفاء الفشل.
- حذف عنصر قبل تحليل مستخدميه وترحيلهم.
- إبقاء مسار قديم قابلًا للوصول بعد استقرار البديل.
- تغيير معايير القبول بعد التنفيذ لإخفاء الانحراف.
- ادعاء الإغلاق دون أثر محفوظ وقراءة راجعة.

## 9. تجميع التغييرات المشتركة

إذا احتاجت عدة رحلات تعديل:

- العقد نفسه.
- العميل المولد نفسه.
- المخطط أو الجدول نفسه.
- الخدمة نفسها.
- Shared Brain نفسه.
- آلة الحالة نفسها.
- إعداد Runtime نفسه.
- مصدر الحقيقة نفسه.

لا تنفذ التغيير داخل كل رحلة.

نفّذه مرة واحدة في وحدة مشتركة، ثم:

1. تحقق من المصدر المركزي.
2. أعد توليد المخرجات المشتقة.
3. حدّث جميع المستهلكين.
4. أزل العقود أو المسارات الموازية.
5. اجعل الرحلات تعتمد على الوحدة المشتركة.
6. أعد الفحوص المتأثرة.
7. لا تكرر العمل نفسه لاحقًا داخل وحدات الرحلات.

عند تنفيذ تطبيق أو سطح أو صفحة أو ميزة أو رحلة، لا تحصر التنفيذ في العنصر المذكور.

تتبّع كل فعل من نية المستخدم إلى:


معالجة إجراء في تطبيق العميل، مثلًا، لا تنتهي عند شاشة العميل إذا كان أثره يجب أن يظهر للشريك أو الكابتن أو الميداني أو العمليات أو الدعم أو التحليلات أو المالية.

- القيود والفهارس.

## 14. استراتيجية التحقق السريعة والدقيقة

بعد كل مهمة، شغّل أقرب فحص قادر على كشف خطئها:

```text
فحص الملف أو الرمز
→ اختبار الوحدة أو الحزمة
→ اختبار التكامل المرتبط
→ affected lint/typecheck/test/build
```

بعد كل وحدة:

```text
فحوص الوحدة
→ الحراس المنطبقة
→ اختبارات العقود أو البيانات أو الصلاحيات المتأثرة
```

عند نقاط التثبيت:

```text
الفحوص الشاملة المنطبقة
→ البناء
→ Runtime
→ Health/Readiness
→ Smoke
→ cross-surface E2E
→ manual UX acceptance
→ final persisted read-back
→ observability/audit verification
```

طبّق نقاط التثبيت:

```text
CHECKPOINT-0:
SHA البداية والحالة الأولية.

CHECKPOINT-1:
إغلاق خط الأساس.

CHECKPOINT-2:
استقرار البيانات والهجرات والعقود والعملاء.

CHECKPOINT-3:
استقرار الخدمات وآلات الحالات.

CHECKPOINT-4:
اكتمال ربط الأسطح وتجربة المستخدم.

CHECKPOINT-5:
نجاح Runtime وSmoke وE2E والقراءة الراجعة النهائية.
```

شغّل الحراس المنطبقة الموجودة فعليًا في المستودع، ومنها في المشروع الحالي:

```powershell
pnpm run guard:foundation
pnpm run guard:journey
pnpm run guard:journey-runtime
pnpm run guard:journey:full
```

لا تدّع تشغيل فحص لم يُشغّل، ولا تحول الأمر المفقود أو البيئة غير المتاحة إلى `PASS`.

لكل فحص سجل:

```text
verificationId
command
environment
prerequisites
baseline SHA
resulting SHA
exit status
actual result
what it proves
what it does not prove
```

## 15. إبطال الأدلة وإعادة فتح الأساس

أي تغيير لاحق في:

- مصدر حقيقة.
- الهوية أو الصلاحيات.
- العقد المركزي.
- العميل المولد.
- المخطط أو الهجرة.
- آلة حالة مشتركة.
- Shared Brain.
- إعداد Runtime تأسيسي.

يجب أن يؤدي إلى:

1. تحديد الوحدات التابعة.
2. تحديد الفحوص التي أصبحت قديمة.
3. إعادة الوحدات المتأثرة إلى `READY` عند الحاجة.
4. إعادة الفحوص المتأثرة.
5. تحديث الأدلة والـSHAs.
6. منع الإغلاق بنتائج سبقت تغيير الأساس.

إذا اكتُشفت فجوة تأسيسية أثناء رحلة:

1. أوقف الرحلة عند حد آمن.
2. سجّل الدليل.
3. صنّف الفجوة.
4. أعد فتح وحدة الأساس المالكة أو أنشئ وحدة جديدة غير متداخلة.
5. أبطل الأدلة التابعة.
6. أعد حساب ترتيب التنفيذ والمسار الحرج.
7. نفّذ إصلاح الأساس.
8. أعد `guard:foundation`.
9. أعد فحوص الوحدات المتأثرة.
10. استكمل الرحلة من آخر نقطة مثبتة.

يُمنع ترقيع الفجوة داخل رحلة واحدة إذا كانت تؤثر في أساس مشترك.

## 16. تصنيف العوائق

صنّف كل عائق إلى:

```text
INTERNAL_FIXABLE_BLOCKER
EXTERNAL_DEPENDENCY
ENVIRONMENT_UNAVAILABLE
MISSING_AUTHORITY
NON_BLOCKING_DEBT
```

القواعد:

- `INTERNAL_FIXABLE_BLOCKER`: يجب معالجته، ولا يسمح بالإغلاق.
- `EXTERNAL_DEPENDENCY`: يسجل بدليل ومالك وشرط إعادة فتح.
- `ENVIRONMENT_UNAVAILABLE`: لا يتحول إلى نجاح؛ تسجل الفحوص غير المنفذة.
- `MISSING_AUTHORITY`: لا تنفذ الإجراء المحظور دون تفويض.
- `NON_BLOCKING_DEBT`: لا يعطل الرحلة إلا إذا ثبت أثره، لكنه يبقى ظاهرًا في التقرير.

لا تستخدم العائق الخارجي لإخفاء خلل داخلي.

## 17. تحديث الحزمة

بعد كل وحدة، حدّث الملفات الحالية دون اختراع مخطط جديد.

### `RESULT.json`

حدّث:

```text
status
baselineSha
resultingSha
completedTaskIds
modifiedPaths
checkResults
blockers
deviations
decision
```

لا تجعل القرار:

```text
PASS
```

مع وجود مانع أو انحراف غير محسوم.

### `EXECUTION.json`

حدّث حالة الوحدة بما يطابق حالتها الفعلية.

### `EXECUTION-ORDER.json`

حدّث حالة الوحدة، ولا تسمح بأكثر من وحدة `IN_PROGRESS`.

### `MANIFEST.json`

حدّث:

```text
latestObservedRemoteSha
status.implementation
status.verification
status.decision
```

بحسب التقدم الحقيقي.

لا تجعل الوحدة `DONE` قبل:

- اكتمال مهامها.
- تسجيل `resultingSha`.
- نجاح جميع الفحوص المطلوبة.
- خلو `blockers`.
- خلو `deviations`.
- قرار `PASS`.

## 18. Commit وPush

أنشئ Commit عند الحدود المنطقية وبعد نجاح فحوص الوحدة أو نقطة التثبيت.

استخدم رسالة تصف النتيجة الفعلية، لا نشاطًا عامًا.

طبّق التفويض:

```text
LOCAL_ONLY:
لا Commit ولا Push.

COMMIT:
Commit محلي فقط.

COMMIT_AND_PUSH:
Commit وPush إلى الفرع المحدد.
```

لا تدمج إلى فرع آخر، ولا تنشئ PR أو Release أو تغيير Production إلا إذا طلبت المهمة الحالية ذلك صراحةً.

## 19. الإغلاق النهائي

لا يصدر قرار النجاح إلا عندما:

- أزيلت الأسباب الجذرية.
- أُغلق خط الأساس.
- أُغلقت كل الوحدات المرتبطة.
- أُزيلت مصادر الحقيقة الموازية.
- أصبحت الملكيات والعقود والحدود متسقة.
- انتقل جميع المستهلكين إلى المصادر الصحيحة.
- نجحت فحوص البيانات والعقود والخدمات والأسطح.
- أصبحت الصفحات والتحكمات والحالات المرتبطة عاملة فعليًا.
- نجحت القراءة الراجعة في جميع الأسطح المستهلكة.
- نجحت الفحوص الإلزامية على الـSHAs المسجلة.
- لا توجد نتيجة قديمة أبطلها تغيير لاحق.
- لا توجد فجوة داخلية مرتبطة وقابلة للمعالجة.
- لا توجد عوائق أو انحرافات غير محسومة.
- لم تتضرر تغييرات غير مرتبطة بالمهمة.

عند استخدام حزمة:

1. اجعل جميع وحدات `EXECUTION-ORDER.json`:
   - `DONE`
2. اجعل جميع وحدات `EXECUTION.json`:
   - `DONE`
3. اجعل جميع `RESULT.json`:
   - `status: DONE`
   - `decision: PASS`
   - `blockers: []`
   - `deviations: []`
   - `resultingSha`: SHA صحيح كامل.
4. حدّث `MANIFEST.json`:
   - `implementation: COMPLETE`
   - `verification: COMPLETE`
   - `decision: CLOSED_WITH_EVIDENCE`
5. أكمل `CLOSURE.md` بالأدلة والـSHAs والرحلات والفحوص والآثار.
6. شغّل:

```powershell
node tools/diagnose-implementing/validate-package.mjs `
  <PACKAGE_PATH> `
  --strict `
  --closure
```

عالج جميع الإخفاقات حتى تكون النتيجة:

```text
Validation summary: 0 error(s)
```

لا تستخدم:

```text
--disposal
```

ولا تحذف الحزمة تلقائيًا.

لا يتم حذفها إلا بطلب صريح، وبعد إثبات أن Runtime والبناء وCI والهجرات والحوكمة والتشغيل لا يعتمد أي منها عليها، ونقل جميع النتائج الدائمة إلى ملاكها الحقيقيين.

## 20. تقرير التسليم

قدّم تقريرًا نهائيًا يحتوي:

```text
repository
branch/ref
starting remote SHA
foundation unit resulting SHAs
foundation verification gate SHA
journey execution base SHA
final implementation SHA
final verification SHA
executed foundation units
executed migration units
executed shared prerequisite units
executed journey units
critical path
actual execution order
reason for each scheduling decision
modified paths
added paths
moved paths
removed paths
root causes resolved
truth owners unified
contracts and generated clients updated
database migrations and data effects
invalidated and rerun checks
commands and actual results
runtime and cross-surface evidence
commits
push result
external blockers
unavailable evidence
final decision
```

القرار النهائي يكون واحدًا فقط:

```text
CLOSED_WITH_EVIDENCE
BLOCKED_WITH_EXPLICIT_CAUSE
```

يُمنع استخدام `CLOSED_WITH_EVIDENCE` إذا بقي:

- خلل داخلي مرتبط وقابل للمعالجة.
- فحص إلزامي فاشل أو غير منفذ دون تصريح.
- عائق أو انحراف غير محسوم.
- دليل قديم سبق تغيير الأساس الذي بُني عليه.
- رحلة أو سطح أو مستهلك مرتبط لم يُغلق.

الصياغتان الآن مستقلتان، قابلتان للنسخ والاستخدام مباشرة، ومتوافقتان مع المولد والقوالب والفاحص الحاليين دون افتراض أوضاع غير مدعومة.

# J003 — دورة حياة Actor

```yaml
owner: Identity
actors: [OPERATOR, CUSTOMER, PARTNER, CAPTAIN, FIELD]
surfaces: [control-panel, app-client, app-partner, app-captain, app-field]
dependencies: [FOUNDATION-00, J002]
assessment_status: NOT_ASSESSED
closure_status: OPEN
```

## النتيجة التشغيلية

تعليق أو إعادة تفعيل Actor بانتقال واضح وسبب ووقت فعال، مع إبطال الجلسات والأجهزة والكاش فورًا وعدم إعادة امتيازات سابقة تلقائيًا.

## الحالة الحالية

- **الموجود المثبت:** مفهوم active/suspended Actors والجلسات موجود إجمالًا.
- **غير المثبت:** جدول الانتقالات، atomic revoke، cache invalidation، effective time، readback عبر جميع الأسطح.
- **الخاطئ المحتمل:** UI يخفي زرًا لكن Backend يقبل، session قديمة تستمر، إعادة التفعيل تستعيد role محذوفًا، local `isActive` يظل حاكمًا.
- **التصحيح المطلوب:** state machine واحدة وversion locking وsession-family revocation داخل مسار موثوق.
- **الإضافات:** reason taxonomy، scheduled transition عند الحاجة، audit وnotification.

## الأسطح

### Control Panel

- صفحة Actor تعرض status الحالي وسبب وآخر transition والجلسات المتأثرة.
- أزرار `تعليق` و`إعادة تفعيل` و`إبطال كل الجلسات` منفصلة.
- confirmation يوضح الأثر ويتطلب reason.
- زر التعليق يتعطل للحالة غير المسموحة ولا يعتمد على الواجهة وحدها.
- بعد النجاح يعاد fetch وتظهر الحالة الجديدة وaudit link.

### التطبيقات

- عند تعليق Actor أثناء الاستخدام: كل mutation التالية ترفض، session refresh تفشل بسبب محدد، وتظهر شاشة blocked.
- لا يعرض التطبيق رسالة «خطأ شبكة» لحالة suspension.
- بعد إعادة التفعيل لا يدخل المستخدم تلقائيًا بجلسة قديمة؛ يتبع policy جلسة جديدة/تفعيل.
- App Partner/Captain/Field تفصل Actor suspension عن Workforce readiness أو assignment block.

## الانتقالات

| الحالة | الأمر | النتيجة | الممنوع |
|---|---|---|---|
| PENDING_ACTIVATION | suspend | SUSPENDED | activate بلا شروط J005 |
| ACTIVE | suspend | SUSPENDED + revoke sessions | mutation بعد effective time |
| SUSPENDED | reactivate | ACTIVE أو PENDING_ACTIVATION حسب السياسة | استعادة roles محذوفة |
| DEACTIVATED | reactivate | فقط بقرار صريح | implicit restore |

## التقنية

- optimistic version أو row lock.
- transition + audit + revoke markers في transaction/atomic orchestration.
- middleware يتحقق من الحالة في كل طلب حساس، لا عند login فقط.
- caches keyed بالActor version وتبطل بالevent.
- reason codes في OpenAPI وUI mapping مركزي.

## الاختبارات

- suspend أثناء refresh/mutation.
- جهازان وoffline reconnect.
- concurrent suspend/reactivate.
- stale operator page.
- removed role قبل reactivate.
- scheduled effective time boundary.
- cross-actor Operator scope.

## التجريب اليدوي

1. سجّل الدخول في كل تطبيق وعلى جهازين.
2. علّق Actor من Control Panel.
3. نفّذ refresh وmutation وoffline reconnect.
4. تحقق من شاشة blocked والنص والزر المتاح.
5. أعد التفعيل وتأكد أن الجلسات القديمة لا تعود.
6. راجع audit والحالة في كل Surface.

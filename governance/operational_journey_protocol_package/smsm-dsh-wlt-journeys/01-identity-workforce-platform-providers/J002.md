# J002 — تزويد Actor والبحث والقراءة

```yaml
owner: Identity
actors: [OPERATOR, CUSTOMER, PARTNER, CAPTAIN, FIELD]
surfaces: [control-panel, app-client, app-partner, app-captain, app-field]
control_panel_sections: [administration, hr, partners]
dependencies: [FOUNDATION-00, J001]
assessment_status: NOT_ASSESSED
closure_status: OPEN
```

## النتيجة التشغيلية

إنشاء Actor واحد موثوق لكل هوية بشرية أو تشغيلية، ثم البحث والقراءة وفق الغرض والصلاحية. لا يجوز أن تنشئ الأسطح نسخًا محلية من الهاتف أو الدور أو حالة المصادقة.

التسلسل: Operator أو orchestration يرسل البيانات الدنيا → normalization للهاتف/المعرفات → uniqueness وidempotency داخل transaction → Actor ينشأ بحالة أولية → audit/outbox → القراءة من Control Panel أو `me` من السطح المملوك → أي بحث داخلي يبقى غير متاح لتطبيقات الأعمال.

## الحالة الحالية

| التصنيف | الحالة الحالية | المطلوب |
| --- | --- | --- |
| الموجود المثبت | Identity Actors ومفاهيم `me` والتفعيل موجودة في المنصة | تحديد operationIds والhandlers والجداول والقيود الفعلية |
| الناقص | جرد الحقول الحاكمة، normalization، pagination، object auth، idempotency | استخراج الأدلة من الكود والعقود والمهاجرات |

| التصحيح | write path واحد، unique normalized identifiers، read models مقيدة | migration/handler/client convergence |
| الإضافات | status lookup بعد unknown result، audit correlation، negative guard للنسخ المحلية | اختبارات Same-SHA |

## الأسطح

### Control Panel

- قائمة Actors مع search/filter/status/type/pagination server-side.
- صفحة تفاصيل تعرض auth-owned fields فقط، مع links إلى Workforce/DSH references لا نسخها.
- زر `إنشاء Actor` يظهر حسب permission؛ form يوضح الحقول الدنيا وحالة uniqueness.
- بعد الحفظ: يعاد fetch من الخادم وتظهر Actor ID والحالة، لا يعتمد على form state.
- أخطاء: duplicate، invalid phone، forbidden، stale، unknown result.

### App Client/Partner/Captain/Field

- لا يوجد بحث Actors.
- تستخدم `me` لقراءة هوية الجلسة والسطح المسموح.
- لا تقبل actorId أو role من local storage كسلطة.
- عند Actor غير موجود/معطل تظهر حالة مناسبة ولا تنشئ Actor تلقائيًا.

## أقسام لوحة التحكم المرتبطة — التحديد التنفيذي الإلزامي

| القسم والمسار | الصفحة/التبويب | ما يجب أن يظهر | التحكمات والأثر | الحالات والصلاحيات | الربط والاختبار اليدوي |
| --- | --- | --- | --- | --- | --- |
| **الإدارة والصلاحيات** `/dsh/administration` | `Actors` → القائمة وActor Detail | auth-owned fields، status/type، normalized identifier masked، references إلى Workforce/DSH، audit/correlation | `إنشاء Actor`، search/filter/sort/pagination، open detail، refresh؛ mutation واحدة idempotent | create/read/search permissions منفصلة؛ duplicate/invalid/forbidden/conflict/unknown-result | Identity generated client؛ أنشئ وكرر الهاتف والنقر، افقد الرد ثم ابحث بالمرجع |
| **الموارد البشرية** `/dsh/hr` | Person/Captain/Field profile → بطاقة `Identity reference` | Actor ID/status/surface readiness فقط؛ لا نسخ phone/roles كحقول HR حاكمة | `فتح Actor في الإدارة` و`بدء provisioning` عبر orchestration؛ لا Create Actor مستقل داخل HR | HR permission + Identity result؛ missing/suspended/linked/conflict | افحص إنشاء Captain/Field من HR وتأكد أن نفس operation تنتج Actor واحدًا ثم readback |
| **الشركاء والمتاجر** `/dsh/partners` و`/dsh/partners/[partnerId]` | Partner onboarding/detail → تبويب `الهوية والفريق` | Actor references للأعضاء والشريك، status وsurface، links لا نسخ auth | `إنشاء/ربط Actor` داخل Onboarding يرسل command الحاكمة؛ invite/search scoped | partner onboarding/team permissions؛ duplicate/cross-partner/unknown-result | أنشئ Partner Actor من onboarding ثم ابحث في الإدارة؛ حاول نفس الهوية من مسار آخر |

أي قسم آخر يحتاج Actor يعرض reference وstatus فقط، ولا يضيف search داخليًا أو write path ثانيًا.

## التحكمات

| التحكم | مصدر القرار | الأثر |
| --- | --- | --- |
| Create Actor | permission + validation | Actor واحد + audit/outbox |
| Search | internal permission + pagination | لا mutation |
| Open detail | object authorization | masked read |
| Refresh | query حقيقية | readback |
| `me` bootstrap | session subject | actor projection للسطح |

## التقنية

- OpenAPI schemas تفصل create request عن read response.
- generated clients فقط.
- handler يطبق normalization قبل uniqueness.
- DB: unique constraints على normalized identifiers وidempotency key/result.
- search يدعم cursor/limit وحدودًا ثابتة.
- PII masking حسب الدور.
- no auto-provisioning من تطبيقات الأعمال ما لم ينص Product Truth عبر orchestration حاكم.

## الحالات والانتقالات

`PENDING_ACTIVATION → ACTIVE → SUSPENDED → DEACTIVATED` حسب الرحلات اللاحقة. J002 ينشئ الحالة الأولية فقط ولا يختصر J003.

## الاختبارات

- same phone بصيغ متعددة.
- same idempotency key/same payload وdifferent payload.
- concurrent create.
- search permission وcross-scope.
- `me` لكل Surface وwrong-surface role.
- response loss after commit ثم lookup.
- route/tab/control binding للأقسام الثلاثة وعدم وجود write path موازٍ.

## التجريب اليدوي

1. أنشئ Actor من `/dsh/administration`.
2. كرر الهاتف بصيغ محلية ودولية وبنقر مزدوج.
3. افقد الرد بعد الإرسال ثم أعد فتح البحث.
4. أنشئ/اربط Actor عبر `/dsh/hr` وPartner onboarding وتحقق من سجل واحد.
5. سجّل الدخول من Surface صحيح وآخر خاطئ.
6. حاول البحث من تطبيق Mobile ومن Operator بلا permission.
7. افحص DB/audit/outbox وتأكد من سجل واحد.

## النتيجة التشغيلية

يجب أن يعرف كل مستهلك هل خدمة Identity قادرة على المصادقة والتحقق وإصدار الجلسات، لا مجرد أن العملية الحية لم تتوقف. النتيجة الصحيحة تفصل بين:

- `HEALTHY`: العملية حية والاعتماديات الأساسية سليمة.
- `DEGRADED`: الخدمة حية لكن اعتمادًا غير حرج أو قدرة فرعية متدهورة.
- `NOT_READY`: لا يجوز توجيه طلبات مصادقة أو تفعيل إليها.

التسلسل: Runtime يبدأ → المهاجرات ومفاتيح التوقيع والاتصال بقاعدة البيانات تتحقق → readiness يفتح → الأسطح تبدأ bootstrap → عند فقد اعتماد حرج تتحول readiness فورًا وتظهر حالة قابلة للفهم → بعد التعافي تعاد القراءة ولا يفترض النجاح من cache قديم.

## الحالة الحالية: الموجود والناقص والخاطئ

| التصنيف | الحالة الحالية | المطلوب لإثباتها |
|---|---|---|
| الموجود المثبت | وجود خدمة Identity وRuntime profile وhealth/readiness ضمن المنصة مثبت إجمالًا | جرد المسارات والhandlers والchecks ومخرجات Runtime على SHA الحالي |
| الناقص | لا يوجد داخل هذا الملف بعد mapping فعلي لكل probe واعتماد وSurface | تسجيل route/operationId/handler/check/timeout والنتيجة في كل Surface |
| الخاطئ المحتمل | false-ready، health يعيد 200 رغم DB/migration/key failure، تسريب config أو stack trace | اختبارات إسقاط DB والمفتاح والمهاجرات والاعتماد الخارجي |
| التصحيح | توحيد health model ومصدر status، fail-closed للجاهزية، reason codes، time budgets | عقد OpenAPI واختبارات Runtime سلبية |
| الإضافات | dependency matrix، readiness transitions، alerting، manual runbook | أدلة Same-SHA |

أي بند غير مقاس يبقى `UNPROVEN` ولا يسجل PASS.

## الأسطح وما يجب أن يظهر

### Control Panel

- صفحة/Widget لصحة الخدمات تعرض Identity منفصلًا عن بقية الخدمات.
- حقول: overall status، DB، migrations، signing keys، clock، dependency latency، آخر نجاح، correlation.
- زر `إعادة الفحص` يستدعي Query حقيقية ولا يغير الحالة يدويًا.
- عند `NOT_READY`: banner أحمر، تعطيل إجراءات إنشاء Actor والتفعيل، وإظهار السبب والخطوة التالية.
- عند `DEGRADED`: banner تحذير مع القدرات المتأثرة، دون إخفاء البيانات التشغيلية القديمة.

### التطبيقات الأربعة

- لا تحتاج Dashboard صحة؛ تحتاج bootstrap gate موحدًا.
- أثناء بدء التطبيق: splash ثم session bootstrap.
- عند Identity unavailable: شاشة service unavailable مع retry آمن، لا logout قسري ولا حذف token.
- عند token invalid فعليًا: انتقال إلى login/activation؛ لا يخلط مع outage.
- App Captain/Field/Partner تعرض readiness المهنية بعد نجاح Identity، لا قبلها.

|---|---|---|---|---|---|

الأقسام الأخرى غير المذكورة لا تملك شاشة صحة Identity مستقلة؛ تستهلك فقط bootstrap/readiness projection المسموحة ولا تنشئ Probe أو Override موازيًا.

## التحكمات والحالات

| التحكم/الحالة | السلوك الصحيح | الاختبار |
|---|---|---|
| Retry health/bootstrap | query فقط مع backoff | نقر متكرر لا يولد storm |
| Refresh service panel | يعيد كل checks ويعرض freshness | DB down ثم up |
| `HEALTHY` | كل الاعتماديات الحرجة PASS | cold start |
| `DEGRADED` | قدرة غير حرجة فاشلة مع reason | provider جزئي |
| `NOT_READY` | يمنع auth mutations | DB/key/migration failure |
| Unknown/timeout | لا يتحول إلى healthy | network timeout |

## التقنية والبرمجة

- OpenAPI يعرّف health/readiness response وreason vocabulary.
- Handler لا يقرأ قيم UI أو flags محلية.
- checks لها timeout مستقل ولا تنتظر بلا حدود.
- readiness يتحقق من migration state ومفتاح التوقيع وقاعدة البيانات.
- logs/metrics لا تحتوي secrets أو raw tokens.
- Runtime healthcheck وCI smoke يستخدمان نفس endpoint الحاكم.
- لا endpoint قديم موازٍ أو shell-specific fallback.

## الاختبارات الآلية

- Unit لكل check وaggregation priority.
- Contract لكل status/reason.
- Integration مع DB unavailable وmigration incomplete وmissing signing key.
- Runtime cold start/restart/dependency loss/recovery.
- Security redaction.
- Frontend bootstrap states لكل Surface.
- Control Panel route/card/action binding للأقسام الثلاثة أعلاه.

## التجريب اليدوي

1. شغّل Runtime من SHA مثبت وتحقق من `HEALTHY` في Control Panel وكل التطبيقات.
2. أوقف DB: يجب `NOT_READY` وتعطيل auth mutations، بينما التطبيقات تعرض outage لا invalid credentials.
3. أعد DB: يجب recovery دون restart يدوي إن كانت السياسة تسمح.
4. اختبر missing key وtimeout وconcurrent probes.
5. راقب logs وNetwork وتأكد من عدم كشف secrets.
6. افتح `/dsh/dashboard` و`/dsh/platform` و`/dsh/administration` واختبر كل بطاقة وتبويب وزر وحالة وصلاحية.
7. أعد تشغيل كل Surface وتحقق من نفس النتيجة.

## النتيجة التشغيلية النهائية

يتخذ الشريك قرارًا واحدًا نهائيًا ضمن مهلة server-authoritative: قبول أو رفض بسبب معتمد. القرار يتحقق من store/team scope وOrder version والحالة الحالية، ويظهر فورًا وبنفس المعنى للعميل وControl Panel. انتهاء المهلة transition حقيقية لا timer محلي.

## تشخيص الحالة الحالية

### الموجود
- Partner Orders screens وOrder lifecycle view models.
- Order truth وoperator workboards في DSH.

### الناقص
- state/transition contract صريح `PENDING_PARTNER | ACCEPTED | REJECTED | TIMED_OUT`.
- rejection reason taxonomy وrequired notes/evidence.
- server deadline وclock skew handling.
- unknown-result recovery بعد decision commit.
- concurrent operator/partner action rules.
- customer messaging وربطها بالسبب الآمن.

### الخاطئ أو الممنوع
- countdown محلي يقرر timeout.
- زر قبول/رفض دون version/idempotency.
- رفض بلا reason أو reason free-text فقط.
- partner member خارج store scope يتخذ القرار.
- surface تعرض accepted بينما truth rejected بسبب optimistic UI غير مصحح.

### التصحيح المطلوب
- domain command `DecidePartnerOrder` واحد.
- deadline/deadline version من الخادم.
- unique final decision وidempotency result.
- generated allowedActions/reasons.
- readback إلزامي بعد unknown result.

### الإضافات المطلوبة
- decision audit with actor/store/reason/deadline.
- timeout worker idempotent.
- operator view للمتابعة لا overwrite صامت.

## منطق التشغيل

- فقط Order `PENDING_PARTNER` وقبل deadline تقبل decision.
- أول transition ناجح يفوز؛ الطلبات التالية تعيد النتيجة النهائية.
- timeout job يستخدم DB time/version ويصدر event.
- rejection reason قد يطلق cancellation/alternative workflow لاحقًا ولا يخلق refund محليًا.
- العميل يرى حالة آمنة ورسالة لا تكشف معلومات داخلية.

## App Partner

- decision sheet مع order summary، deadline، Accept، Reject، reason selector، note مشروط.
- أزرار disabled أثناء الإرسال وبعد انتهاء المهلة.
- confirm للرفض، double-tap protection، unknown-result screen مع `تحقق من القرار`.
- حالات stale order، permission revoked، timeout race، already decided.

## App Client

- حالة `بانتظار تأكيد المتجر` ثم accepted/rejected/timed out.
- لا يعرض reason داخليًا غير مناسب؛ يعرض الخيارات التالية إن وجدت.
- refresh/reconnect يعيد الحقيقة.

## Control Panel

- live countdown من server timestamps، decision actor/reason/version.
- لا زر عام لتغيير الحالة؛ أي override command مستقل بصلاحية وسبب.
- diagnostics للـtimeout worker/event delivery.

## العقود والبيانات

- decision endpoint يطلب order version/idempotency/reason.
- DB unique decision/order transition constraints.
- server timestamp وdeadline stored.
- append-only audit/outbox.
- reason vocabulary مركزية ومترجمة في presentation.

## الاختبارات الآلية

- double accept/reject.
- accept vs timeout race.
- stale version.
- unauthorized store/team member.
- unknown result after commit.
- operator concurrent action.
- customer/partner/control-panel parity.

## التجريب اليدوي

1. افتح Order في App Partner واقبلها.
2. كرر القرار واضغط من جهازين.
3. اختبر الرفض بكل reasons والمتطلبات.
4. دع المهلة تنتهي مع التطبيق مفتوحًا ومغلقًا.
5. افصل الشبكة بعد القرار ثم تحقق من readback.
6. اسحب صلاحية الموظف أثناء الشاشة.
7. قارن الحالات على Client وControl Panel.

## النتيجة التشغيلية

Write path واحد للavailability/stock signal/min/max/step/reservation policy مع concurrency آمنة وإعادة تحقق في Cart/Checkout. يجب أن يكون واضحًا هل النظام يدير quantity دقيقة أم availability signal فقط لكل نوع Store.

## الحالة الحالية

- stock/availability endpoints موجودة أو متوقعة؛ model policy غير مثبت لكل vertical.
- الخطر: negative stock، oversell، UI local quantity truth، bulk update بلا version، availability لا تبطل cache.
- المطلوب: product-level stock policy، versioned adjustments، reservations أو explicit no-reservation policy، audit.

## App Partner

- inventory list/search/filter وbulk update.
- controls: set available/unavailable، adjust quantity، set min/max/step، pause.
- يعرض server version وlast updated/source.
- conflict dialog عند stale update؛ لا silent overwrite.

## App Field

- verification/adjustment ضمن assignment وevidence عند السياسة.
- barcode scan، current value readback، offline queue.
- لا يسمح تعديل Store خارج scope.

## Control Panel

- inventory diagnostics/history/adjustments/reservations.
- intervention requires reason.
- alerts للnegative/oversell/drift.

## App Client

- availability وquantity limits واضحة.
- plus/minus/add buttons تتعطل حسب server rules.
- cart/checkout يعرض `OUT_OF_STOCK`, `QUANTITY_CHANGED`, `LIMIT_CHANGED` ويقدم update/remove.

## التقنية

- nonnegative checks وversion/ledger-like adjustment history عند quantity.
- idempotent adjustment source.
- reservation transaction أو documented optimistic recheck.
- events/cache/search invalidation.
- order placement atomicity مع stock policy.

## الاختبارات

- concurrent decrement/reservation.
- duplicate adjustment.
- negative/overflow quantity.
- min/max/step violations.
- stale offline update.
- checkout race.

## التجريب اليدوي

1. عدّل stock من Partner/Field متزامنًا.
2. أضف من جهازين حتى الحد.
3. غيّر availability أثناء Cart/Checkout.
4. كرر adjustment وفقد الرد.
5. اختبر bulk partial failure.
6. افحص history/order consistency.

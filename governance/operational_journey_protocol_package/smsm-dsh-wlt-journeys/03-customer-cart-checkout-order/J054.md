## النتيجة التشغيلية النهائية

يمتلك DSH حقيقة Order واحدة وحالة انتقالية موحدة وسجل timeline append-only. كل Surface يرى projection ملائمة لدوره من نفس الحقيقة، بلا enums أو timelines موازية. الأحداث المتأخرة أو المكررة لا تعيد الحالة للخلف ولا تكشف بيانات غير لازمة.

## تشخيص الحالة الحالية

### الموجود
- order truth handlers/view-models/lifecycle في DSH.
- أسطح الطلب موجودة للعميل والشريك والكابتن والميدان والعمليات.

### الناقص
- state machine authoritative كاملة مع transition owners/preconditions.
- event/version ordering وreplay rules.
- projection/redaction matrix لكل Surface.
- timeline vocabulary وترجمة موحدة.
- stale indicator وreadback after reconnect.
- tests لكل transition وout-of-order event.

### الخاطئ أو الممنوع
- حالة محلية مختلفة في كل تطبيق.
- surface يشتق حالة مالية أو تشغيلية من نصوص.
- تحديث state مباشرة من أكثر من handler دون domain command.
- timeline mutable أو حذف event تاريخي.
- Captain/Field يرى customer/partner data غير لازم.

### التصحيح المطلوب
- domain state machine وحيد.
- transition commands بصلاحيات وversions.
- generated lifecycle types أو shared view model مشتق لا authority.
- projection adapters لكل actor.
- إزالة aliases/enums المكررة والمسارات القديمة.

### الإضافات المطلوبة
- transition matrix في الملف والعقد.
- order timeline inspector.
- stale/reconnect behavior.
- reason/evidence requirements للحالات الحساسة.

## منطق التشغيل

- كل transition يتحقق من current version/state/actor/permission/preconditions.
- events append-only مع sequence/version؛ duplicate ignored، gap triggers reconciliation، older event لا يخفض state.
- financial substate يأتي من WLT reference ويعرض منفصلًا عن operational state.
- cancellation/exception/support لا تكتب state عشوائيًا بل commands محددة.

## App Client

- Order list/detail، current status، timeline، ETA/fulfillment، support/cancel controls حسب eligibility.
- states loading/empty/stale/offline/updated/cancelled/completed/exception.
- لا تظهر controls غير مسموحة؛ disabled control يوضح السبب إذا يجب عرضه.
- pull-to-refresh/readback after reconnect.

## App Partner

- inbox/detail مع preparation actions في الرحلات التالية.
- customer data masked للحد التشغيلي.
- timeline يوضح المطلوب من الشريك والمهل.
- no manual arbitrary status selector.

## App Captain

- يرى assigned order فقط وحالات route/handoff اللازمة.
- controls تظهر وفق assignment/state.
- بعد completion تقل البيانات الحساسة.

## App Field

- يرى الطلب فقط عند assignment/support visit مصرح.
- actions محكومة ولا يغير lifecycle خارج صلاحياته.

## Control Panel

- live workboard، order detail، authoritative timeline، transition/evidence/audit.
- controls role-scoped مع reason/confirmation، no dropdown عام للحالة.
- diagnostics للversion gaps/projection lag/event delivery.

## العقود والبيانات

- OrderState وTransitionCode وTimelineEvent مركزية.
- order version optimistic locking.
- append-only events/outbox/projection checkpoints.
- row/object authorization وoperator context isolation.
- WLT refs منفصلة ومقروءة عبر facade.

## الاختبارات الآلية

- كل transition صالح/غير صالح.
- concurrent transitions.
- duplicate/out-of-order/gap events.
- projection parity/redaction.
- stale client command.
- IDOR عبر كل actor.
- restart/rebuild projection.
- financial/operational separation.

## التجريب اليدوي

1. أنشئ Order وتتبعها على الأسطح الخمسة.
2. نفّذ transitions متسلسلة ثم محاولة غير صالحة.
3. أرسل duplicate/out-of-order events في بيئة اختبار.
4. افصل App Client/Captain ثم أعد الاتصال.
5. تحقق من masking واختفاء controls حسب الدور.
6. أعد بناء projection وقارن الحقيقة.
7. راجع audit/timeline/version في Control Panel.

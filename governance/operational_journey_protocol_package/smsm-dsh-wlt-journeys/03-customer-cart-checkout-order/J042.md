## النتيجة التشغيلية النهائية

عنوان العميل سجل DSH محكوم يضم label، نقطة جغرافية، تفاصيل وصول، ونسخة مخفية للاستخدام التشغيلي. لا يُكشف العنوان الكامل للكابتن أو الميدان إلا في المرحلة المسموحة من الطلب، ولا يحتفظ Provider بحقيقة عنوان. التحقق الجغرافي enrichment فقط ويمكن إعادة بنائه.

## تشخيص الحالة الحالية

### الموجود المثبت
- توجد عقود ومسارات لعناوين العميل والخصوصية في DSH.
- App Client هو مالك تجربة الإنشاء والتعديل.
- Captain/Field يحتاجان projection محدودة زمنياً أثناء التنفيذ.

### الناقص
- lifecycle صريح: `DRAFT | VERIFIED | ACTIVE | ARCHIVED | DELETED`.
- سياسة default address ذرية.
- قواعد precision وgeofence وprovider provenance.
- جدول كشف PII حسب actor/order state.
- conflict/versioning وsoft-delete retention.
- اختبار فعلي لمنع القراءة خارج الطلب أو بعد اكتماله.

### الخاطئ أو الممنوع
- إرسال raw address لكل أسطح العمليات منذ إنشاء الطلب.
- اعتماد نص Provider كحقيقة دائمة دون الإحداثيات الأصلية.
- تخزين نسخة كاملة في state أو logs أو analytics.
- حذف العنوان المستخدم تاريخيًا بما يكسر أدلة الطلب.
- السماح بتعيين أكثر من default بسبب race.

### التصحيح والإضافات
- فصل `customer_address` عن `order_delivery_snapshot`.
- إنشاء masked operational projection بمدة وصلاحية.
- تطبيق version وidempotency وunique default constraint.
- إضافة audit للكشف والتعديل والحذف.
- إضافة شاشة إدارة العناوين وprivacy access history.

## منطق التشغيل

- العميل ينشئ/يعدل/يؤرشف عنوانه؛ الطلب يلتقط snapshot immutable عند التأكيد.
- Provider يعيد normalized label/confidence فقط مع حفظ provenance.
- Captain يرى تعليمات لازمة بعد assignment؛ قبل ذلك يرى منطقة تقريبية فقط.
- بعد التسليم أو الإلغاء تنتهي صلاحية projection وتبقى أدلة الطلب حسب retention.
- تغيير العنوان لا يغير طلبًا مؤكدًا إلا عبر workflow محكوم.

## App Client

- قائمة العناوين مع default badge، edit، delete/archive، set default، add new.
- خريطة اختيار pin، زر `استخدم موقعي`، حقل وصف المبنى/الطابق/علامة، معاينة الخصوصية.
- حالات: permission denied، provider unavailable، low confidence، outside service area، duplicate candidate، conflict، offline draft.
- لا يظهر نجاح حتى GET readback؛ double-tap لا ينشئ سجلين.

## App Captain

- قبل assignment: لا عنوان كامل.
- بعد assignment والمرحلة المسموحة: pin، تعليمات الوصول الضرورية، زر navigation، call proxy إن وجد.
- أزرار `تعذر الوصول` و`طلب مساعدة` لا تكشف بيانات إضافية تلقائيًا.
- بعد completion: تختفي التفاصيل الحساسة ويظل مرجع masked.

## App Field

- لا يرى عنوان العميل افتراضيًا.
- يظهر فقط في رحلة دعم/تحقق مصرح بها مع purpose banner ومدة انتهاء.
- كل كشف يسجل audit؛ يمنع screenshots داخل التطبيق إن كانت السياسة تدعم ذلك أو يعرض watermark.

## Control Panel

- بحث masked، خريطة تقريبية افتراضيًا، زر كشف مؤقت بصلاحية وسبب.
- تبويبات: lifecycle، الاستخدام في الطلبات، access audit، provider diagnostics.
- أدوات archive/restore وفق السياسة؛ لا تعديل snapshot طلب قديم.

## التقنية والبيانات

- OpenAPI منفصل self-service وoperational projection.
- DB constraints: owner، version، one-default، valid coordinate range، archived visibility.
- order snapshot immutable مع address_version/source_id.
- encryption at rest للحقول الحساسة حيث معتمد.
- logs/metrics تستخدم IDs ومناطق لا النص الكامل.

## الاختبارات الآلية

- IDOR وcross-actor address access.
- two-default race.
- delete address referenced by order.
- captain access before/after allowed state.
- provider timeout/low confidence/fallback.
- coordinate boundary/geofence.
- log redaction وanalytics payload scan.
- offline retry وunknown result.

## التجريب اليدوي

1. أضف عنوانًا من الخريطة ومن إدخال يدوي.
2. ارفض location permission ثم أدخل pin يدويًا.
3. عيّن default من جهازين بالتزامن.
4. أنشئ طلبًا ثم عدّل العنوان الأصلي وتحقق من ثبات snapshot.
5. تحقق من ظهور العنوان للكابتن قبل/بعد assignment وبعد completion.
6. حاول Operator وField بلا صلاحية ثم بكشف مؤقت.
7. عطّل Provider وتحقق من fallback وعدم فقد pin.
8. افحص audit والـlogs والـDB.

## النتيجة التشغيلية النهائية

يختار العميل نمط تنفيذ متاحًا فعليًا من DSH مثل `DELIVERY | PICKUP | PARTNER_DELIVERY` وفق المتجر والعنوان والقدرة والسياسات. النمط المختار يغيّر المتطلبات والرسوم والوقت والمسؤوليات بصورة صريحة، ولا يبقى مجرد toggle بصري.

## تشخيص الحالة الحالية

### الموجود

- delivery/pickup/partner delivery concepts ومسارات handoff في DSH.
- Partner وCaptain surfaces تتأثر بالنمط بعد إنشاء الطلب.

### الناقص

- mode capability contract موحد مع reasons ومتطلبات كل mode.
- transition rules عند تغيير mode داخل Checkout.
- ownership للمسؤولية والhandoff لكل mode.
- UI parity وcopy واضحة.
- tests لتغير الرسوم/serviceability والجدول.

### الخاطئ أو الممنوع

- إظهار mode غير مدعوم للمتجر.
- تغيير mode دون إبطال quote وETA وaddress requirements.
- استخدام نفس order states لكل mode دون mapping واضح.
- تكليف Captain بطلب Pickup.
- Partner delivery دون إثبات مسؤولية وتسليم.

### التصحيح والإضافات

- fulfillment capability endpoint/section في Checkout.
- state machine وmode-specific requirements.
- mode badges في كل Surface.
- diagnostics ومسار fallback/unsupported.
- إزالة toggles والقيم الافتراضية المحلية.

## منطق التشغيل

- DSH يعيد modes المتاحة وreason للغير متاح.
- اختيار mode يثبت version داخل intent ويعيد حساب serviceability/quote/ETA.
- Delivery يتطلب عنوانًا؛ Pickup يتطلب pickup instructions/window؛ Partner Delivery يحدد مسؤولية الشريك ولا يدخل dispatch المركزي إلا حسب السياسة.
- لا يمكن تغيير mode بعد نقطة معينة إلا عبر workflow تعديل محكوم.

## App Client

- بطاقات modes مع الوصف والوقت والرسوم والمتطلبات.
- controls: select، details، change، resolve prerequisite.
- selected state واضح وغير معتمد على اللون وحده.
- حالات unavailable/temporarily disabled/expired/recalculating.
- عند التغيير تظهر التعديلات في السعر والوقت قبل التأكيد.

## App Partner

- يرى mode على Order وبوضوح من المسؤول عن handoff.
- للPickup: controls `جاهز للاستلام` وverify customer handoff في رحلات لاحقة.
- للPartner Delivery: يظهر workflow الخاص وشروطه.
- لا يستطيع تغيير اختيار العميل منفردًا بعد confirmation.

## App Captain

- لا يظهر الطلب إلا إذا mode يتطلب Captain.
- badge وتعليمات handoff متوافقة؛ no pickup assignment.
- أي mode mismatch يظهر incident ولا يتم تجاوزه محليًا.

## التقنية والبيانات

- enum/version مركزي في OpenAPI، لا strings متفرقة.
- fulfillment snapshot في intent/order.
- DB constraints تمنع assignment غير المتوافق.
- events تتضمن mode version والمسؤولية.
- pricing/dispatch integrations تعتمد snapshot نفسها.

## الاختبارات الآلية

- unsupported mode selection.
- mode change يعيد serviceability/quote.
- delivery بلا address وpickup مع address غير لازم.
- pickup assignment to captain blocked.
- partner delivery responsibility.
- stale mode capability.
- UI control mapping لكل mode/reason.
- section action/owner mapping.

## التجريب اليدوي

1. اختبر متجرًا يدعم Delivery فقط ثم عدة modes.
2. بدّل mode داخل Checkout وتحقق من Operations/Finance.
3. أنشئ Pickup وتحقق من Partner وغياب Captain assignment.
4. أنشئ Partner Delivery وتحقق من المسؤولية.
5. عطّل mode من Store/Platform أثناء intent وحاول confirmation.
6. قارن Analytics وApp Client وControl Panel readback.

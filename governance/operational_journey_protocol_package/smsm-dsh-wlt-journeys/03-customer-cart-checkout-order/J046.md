## النتيجة التشغيلية النهائية

يقرر DSH بصورة حتمية وقابلة للتفسير هل يستطيع المتجر خدمة عنوان العميل الآن، وما نمط التنفيذ المتاح، وما ETA التقديري. يعتمد القرار على النطاق، الجدول، القدرة، حالة المتجر، الكتالوج، سياسات التسليم، واعتماديات Providers. لا يحسب أي Surface هذه الحقيقة محليًا، ولا يتحول ETA التقديري إلى وعد صامت.

## تشخيص الحالة الحالية

### الموجود
- عقود `cart-serviceability` ومسارات اكتشاف وعناوين موجودة في DSH.
- Provider routing/maps يمد DSH بمدخلات تقديرية.
- Store publication وschedule وdelivery pricing مؤثرات معروفة.

### الناقص
- decision model موحد يحتوي `serviceable`, `modes`, `reason_codes`, `eta_window`, `quote_version`, `expires_at`.
- ترتيب واضح لكل rule وأولوية reason عند تعدد أسباب المنع.
- cache/TTL وrevalidation عند الانتقال من Storefront إلى Cart وCheckout.
- capacity/readiness inputs موحدة وغير مشتقة من UI.
- diagnostics وwhat-if simulator في Control Panel.
- contract لاختلاف delivery/pickup/partner-delivery.

### الخاطئ أو الممنوع
- عرض `متاح` بسبب وجود متجر فقط.
- حساب ETA داخل التطبيق أو تثبيت رقم افتراضي.
- السماح بالانتقال إلى Checkout بقرار منتهي.
- دمج provider route failure مع `OUTSIDE_SERVICE_AREA` دون تمييز.
- إخفاء سبب عدم الخدمة برسالة عامة لا تساعد المستخدم أو المشغل.

### التصحيح المطلوب
1. إنشاء serviceability decision engine واحد داخل DSH.
2. فصل rule inputs عن provider estimates.
3. تثبيت reason vocabulary وترجمتها في presentation فقط.
4. إصدار decision token/version يعاد التحقق منه.
5. إزالة أي `isServiceable` أو ETA hardcoded/local override في الواجهات.

### الإضافات المطلوبة
- support diagnostics trace.
- capacity degradation states.
- alternate modes/nearby stores suggestions وفق Product Truth.
- metrics لكل reason وdecision latency.

## منطق التشغيل

التسلسل: validate actor/address/store → publication → service-area effectivity → schedule → catalog readiness → fulfillment modes → capacity → provider route estimate → pricing prerequisites → decision. القرار لا يثبت السعر المالي، بل يرفق مراجع quote لاحقة. كل نتيجة لها TTL ويجب إعادة التحقق عند تغيير address/store/cart/time.

## App Client

- في Storefront: banner `يوصل إليك` أو reason واضح، ETA range وتاريخ تحديث.
- controls: `تغيير العنوان`، `اختر الاستلام`، `عرض متاجر بديلة`، `إعادة المحاولة`.
- عند قرار منتهي: loading قصير ثم refresh؛ لا يكمل Add/Checkout اعتمادًا على cache.
- حالات: outside area، closed، capacity full، provider unavailable، pickup only، temporary unavailable، unknown result.
- لا يظهر ETA رقمًا واحدًا إذا العقد window.

## App Partner

- يرى serviceability readiness لامتلاكه: service areas، schedule، capacity، delivery mode، provider connectivity.
- controls تفتح الرحلات المالكة للتعديل، لا تغير decision مباشرة.
- preview بسياق address/time مع reason trace محدود لا يكشف بيانات العميل.

## Control Panel

- simulator: store + masked address + time + cart characteristics.
- يعرض rule-by-rule result، input versions، provider provenance، expiry.
- controls: إعادة تقييم، فتح مالك السياسة، فتح service-area، فتح capacity incident.
- لا يوجد زر force serviceable؛ الاستثناءات تمر change workflow مصرحًا.

## العقود والباك إند والبيانات

- OpenAPI schema ثابت للقرار والreasons والmodes والTTL.
- DB projections للنطاق/الجدول/القدرة مع version/effectivity.
- provider calls محاطة timeout/circuit breaker؛ failure reason مستقل.
- idempotent evaluate endpoint؛ no mutation side effects.
- observability: decision duration، reason distribution، stale-token rejection.

## الاختبارات الآلية

- boundary داخل/خارج polygon وعلى الحافة.
- schedule transition والtimezone.
- capacity exhaustion/recovery.
- provider timeout مع fallback/no fallback.
- decision expiry ثم checkout rejection.
- pickup-only/partner-delivery modes.
- cache partitioning بين addresses.
- parity بين App Client وControl Panel simulator.

## التجريب اليدوي

1. اختبر عنوانًا داخل النطاق وخارجه وعلى الحافة.
2. غيّر الوقت عبر فتح/إغلاق المتجر.
3. استنزف capacity ثم أعدها.
4. عطّل routing provider وراقب reason المحدد.
5. اترك decision تنتهي ثم حاول Checkout.
6. بدّل إلى Pickup وتحقق من إعادة حساب المسار.
7. قارن App Client مع Partner readiness وControl Panel trace.

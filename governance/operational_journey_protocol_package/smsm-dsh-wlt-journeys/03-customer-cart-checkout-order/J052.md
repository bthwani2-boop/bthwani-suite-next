## النتيجة التشغيلية النهائية

يعرض DSH وسائل الدفع المؤهلة للسياق من WLT عبر facade، ويطلب إنشاء Payment Session أولية من WLT دون امتلاك حالة مالية. العميل يختار capability متاحة، وتعود session/reference/status/version وnext action. لا يوجد Provider secret أو status مالي يدوي في DSH أو الواجهات.

## تشخيص الحالة الحالية

### الموجود
- WLT payment session contracts/controllers وDSH checkout handoff.
- generated WLT OpenAPI aliases وحراس مالية.

### الناقص
- eligibility matrix حسب currency/amount/actor/store/mode/provider health.
- lifecycle موحد للـsession والnext actions.
- unknown-result recovery بعد إنشاء session.
- timeout/expiry/replace rules.
- redaction وsupport visibility.
- E2E proof من اختيار الطريقة حتى readback.

### الخاطئ أو الممنوع
- تعريف payment statuses أو envelopes يدويًا في DSH.
- استدعاء WLT أو Provider مباشرة من App Client.
- إنشاء أكثر من session فعالة لنفس intent دون policy.
- إظهار `تم الدفع` قبل WLT authoritative readback.
- تخزين card/provider secrets في DSH أو logs.

### التصحيح المطلوب
- Payment capability endpoint عبر DSH facade.
- WLT-owned create/read/cancel/replace session.
- idempotency key مشتق من checkout intent/version.
- mapping presentation فقط داخل DSH shared frontend.
- إزالة legacy/manual payment types والبقايا.

### الإضافات المطلوبة
- next-action renderer محكوم.
- Control Panel masked session inspector.
- provider health impact وcustomer-safe messages.
- recovery action `تحقق من حالة الدفع`.

## منطق التشغيل

- DSH يرسل context/reference وWLT يقرر methods/capabilities.
- create session idempotent؛ duplicate request يعيد المرجع نفسه.
- status authority في WLT: `CREATED | REQUIRES_ACTION | PROCESSING | SUCCEEDED | FAILED | EXPIRED | CANCELLED | UNKNOWN` وفق العقد الفعلي.
- DSH لا يؤكد Order اعتمادًا على client callback وحده.
- COD إن كان method يمر أيضًا عبر WLT policy لا boolean محلي.

## App Client

- قائمة وسائل مؤهلة مع الرسوم/التعليمات القادمة من العقد.
- controls: select method، continue، perform next action، retry، verify status، choose another method.
- حالات provider unavailable، session expired، action cancelled، processing، unknown result.
- sensitive fields تستخدم components/provider SDK معتمد دون مرور raw data عبر DSH.
- لا success screen قبل WLT readback.

## App Partner

- يرى payment readiness/order payment summary فقط بعد الصلاحية.
- لا يرى وسيلة العميل الحساسة أو provider payload.
- pending/failed تظهر كحالة تشغيلية لا تسمح بالتحضير إذا السياسة تمنع.

## العقود والبيانات

- DSH facade contract مرتبط بـWLT generated client.
- WLT session table unique idempotency/checkout reference، expiry/version.
- service auth وoperator context للقراءات الداخلية.
- webhook/callback signatures في WLT فقط.
- audit/redaction/correlation end-to-end.

## الاختبارات الآلية

- duplicate create وnetwork loss after commit.
- provider timeout/callback replay/out-of-order.
- session expiry/replacement.
- wrong actor/order IDOR.
- client callback spoof.
- COD eligibility.
- secret/log scan.
- DSH/WLT status mapping completeness.
- section action/visibility binding.

## التجريب اليدوي

1. افتح طرق الدفع المؤهلة لسياقات مختلفة.
2. أنشئ session واضغط Continue مرتين.
3. افصل الشبكة بعد الإنشاء ثم استخدم verify status في App/Operations/Finance.
4. نفّذ success/failure/cancel/expiry عبر simulator.
5. حاول spoof callback أو قراءة session لعميل آخر.
6. تحقق من Partners/Support دون بيانات حساسة.
7. راجع Platform provider وWLT DB/audit/reconciliation refs.

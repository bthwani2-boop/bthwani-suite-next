## النتيجة التشغيلية النهائية

يؤكد DSH Checkout Intent صالحة ويُنشئ Order واحدة ذرّيًا مع snapshots ومراجع الدفع والتسعير والعنوان والfulfillment. أي إعادة إرسال أو انقطاع بعد commit يعيد Order نفسها. لا توجد طلبات يتيمة أو مزدوجة أو Payment effect غير مربوط.

## تشخيص الحالة الحالية

### الموجود
- Orders/checkout handlers وorder truth components في DSH.
- idempotency patterns مستخدمة في أجزاء من المستودع.

### الناقص
- transaction boundary موثقة بين intent/order/outbox/cart conversion.
- uniqueness على checkout intent/idempotency key.
- compensation/reconciliation لعلاقات WLT الخارجية.
- explicit response للـunknown result.
- proof لمنع duplicate partner notifications.
- immutable snapshots كاملة.

### الخاطئ أو الممنوع
- إنشاء Order من client payload بدل server intent.
- mark cart converted قبل ضمان Order أو العكس دون transaction.
- إعادة call إلى WLT بلا idempotency.
- success UI من timeout أو local generated ID.
- إرسال event قبل commit أو إرسال مكرر بلا dedupe.

### التصحيح المطلوب
- `ConfirmCheckout` command وحيد.
- DB transaction: lock/validate intent → insert order/snapshots → convert cart → outbox → commit.
- unique constraints وidempotency result storage.
- post-commit WLT/readback reconciliation حسب boundary.
- إزالة أي alternate create-order routes غير محكومة.

### الإضافات المطلوبة
- order creation diagnostics.
- reconciliation job للنتائج الخارجية المجهولة.
- negative tests وfault injection في كل نقطة.

## منطق التشغيل

الحالات: intent `READY→CONFIRMING→CONFIRMED`; order يبدأ `PLACED` أو الحالة المعتمدة. إذا الطلب موجود لنفس intent يعاد كما هو. إذا فشل قبل commit فلا Order ولا conversion. إذا نجح commit وفشلت الاستجابة، GET by intent/idempotency يعيد النتيجة. الأحداث تخرج من outbox بعد commit.

## App Client

- زر `تأكيد الطلب` واحد، disabled أثناء confirm.
- progress واضح ولا يسمح الرجوع لتكرار الطلب دون recovery.
- unknown result يعرض `نتحقق من طلبك` مع action readback لا `فشل` مباشر.
- success يعرض Order ID من الخادم والملخص snapshot.
- duplicate tap/relaunch يعيد نفس Order.

## App Partner

- يظهر Order مرة واحدة في inbox بعد event/read model.
- لا duplicate alerts أو cards.
- payment/fulfillment readiness واضحة قبل قبول الرحلة التالية.

## العقود والبيانات

- confirm endpoint يتطلب intent id/version/hash وidempotency key.
- unique constraints: intent→order one-to-one، idempotency scoped actor/operation.
- immutable order snapshots.
- outbox dedupe key/event version.
- error vocabulary: stale/expired/blocked/already-confirmed/unknown.

## الاختبارات الآلية

- double click/concurrent confirm.
- crash قبل/بعد insert/commit/outbox.
- response loss after commit.
- stale intent/quote/payment state.
- WLT timeout/replay.
- duplicate event consumer.
- cart conversion consistency.
- unauthorized actor/IDOR.
- section diagnostics/action permission mapping.

## التجريب اليدوي

1. أكد طلبًا طبيعيًا وتحقق من كل Surface.
2. اضغط الزر بسرعة ومن جهازين.
3. افصل الشبكة لحظة confirmation ثم أعد فتح التطبيق.
4. استخدم fault injection قبل commit وبعده.
5. تحقق من Operations/Finance وCart converted وOrder واحدة وoutbox event واحد منطقيًا.
6. راقب Partner inbox وPlatform/Audit timeline.
7. أعد إرسال نفس idempotency key.

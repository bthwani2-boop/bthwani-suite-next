## النتيجة التشغيلية النهائية

تستعاد السلة نفسها عبر الأجهزة والجلسات ضمن Actor واحد، مع merge policy معلنة عند guest/auth أو offline/online. الخادم هو الحكم، والعميل يحتفظ cache مؤقتًا مع version ولا يخلق سلة ثانية أو يفقد تعديلًا بصمت.

## تشخيص الحالة الحالية

### الموجود
- session/device management في Identity.
- Cart domain في DSH وmobile runtime متعدد الأسطح.

### الناقص
- guest cart policy وهل هي مطلوبة أصلًا.
- merge algorithm وconflict UX.
- resume token/version بعد reinstall/login.
- offline queue limits/order/deduplication.
- expiration policy وإشعارات المستخدم.
- اختبار multi-device runtime حقيقي.

### الخاطئ أو الممنوع
- last-write-wins صامت بين الأجهزة.
- دمج quantities أو options دون قواعد موثقة.
- إرسال queue قديمة بعد تحول السلة إلى order.
- استخدام device storage كمصدر دائم.
- نجاح مزعوم أثناء offline دون pending state.

### التصحيح المطلوب
- server sync protocol مع version/cursor.
- merge command idempotent ونتيجة تفصيلية.
- invalidation بعد conversion/expiry/logout حسب السياسة.
- frontend sync controller واحد بدل منطق موزع.

### الإضافات المطلوبة
- شاشة conflict/merge summary عند الحاجة.
- sync status وlast updated.
- diagnostics للأجهزة والqueues دون كشف PII.

## منطق التشغيل

- عند startup/login: fetch authoritative cart ثم reconcile pending commands.
- الأوامر القديمة ذات base version منتهية تعود conflict ولا تطبق عميانيًا.
- guest-to-auth merge إن كان معتمدًا ينتج سجلًا واحدًا وmerge report.
- بعد `CONVERTED` ترفض كل queued mutations القديمة.
- expiration لا تحذف evidence المطلوبة وتظهر للمستخدم بوضوح.

## App Client

- sync indicator غير مزعج، pending badge عند offline، conflict sheet عند اختلاف غير آمن.
- controls: `مزامنة الآن`، `مراجعة التغييرات`، `استخدام نسخة الخادم`، `إعادة تطبيق عناصر صالحة`.
- لا يظهر cart badge خاطئ بعد login/logout/reinstall.
- حالات: offline pending، stale، merging، conflict، expired، converted.

## Control Panel

- cart sync diagnostics: devices/session refs، versions، pending/replayed command IDs، merge events.
- controls: invalidate corrupt sync token أو trigger readback ضمن صلاحية؛ لا اختيار نسخة نيابة عن العميل دون workflow.

## التقنية والبيانات

- command IDs مستقرة، ordered queue، per-actor partition.
- merge rules deterministic وunit-tested.
- secure local storage للحد الأدنى دون PII زائد.
- telemetry لا ترسل محتوى الملاحظات أو items كاملة.
- retention للqueues/idempotency records.

## الاختبارات الآلية

- جهازان يعدلان quantity/options.
- offline queue ثم server change.
- logout/login Actor مختلف على الجهاز نفسه.
- reinstall/resume.
- guest merge إن كان منطبقًا.
- queue بعد order conversion.
- expiry boundary وclock skew.
- duplicate replay.

## التجريب اليدوي

1. افتح الحساب على جهازين وعدّل السلة بالتزامن.
2. افصل أحد الجهازين، نفّذ عدة أوامر، عدّل الآخر، ثم أعد الاتصال.
3. جرّب logout إلى Actor آخر وتحقق من عدم تسرب السلة.
4. أعد تثبيت التطبيق أو امسح cache ثم سجّل الدخول.
5. أنشئ Order بينما جهاز آخر offline ثم أعده.
6. افحص merge/conflict UI وControl Panel events.

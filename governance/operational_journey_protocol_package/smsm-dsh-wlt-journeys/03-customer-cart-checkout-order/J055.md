## النتيجة التشغيلية النهائية

يوفر Control Panel لوحات عمل مشتقة من حقيقة الطلب مع queues وأولويات وSLA قابلة للتفسير، بينما تعرض التطبيقات طلبات مساعدة مرتبطة بالطلب والدور. أي تدخل تشغيلي هو command محكوم بصلاحية وسبب وموافقة عند الحاجة، وليس تعديل DB أو state مباشرًا.

## تشخيص الحالة الحالية

### الموجود
- Operations Hub/Command Center/Order workboards وsupport/special request handlers.
- Platform change workflows لبعض السياسات.

### الناقص
- registry موحد لكل queue/card/action ومالكها.
- SLA clocks وpause/resume rules.
- command eligibility وapproval matrix.
- request lifecycle بين الأسطح.
- dedupe/assignment/claim semantics.
- manual acceptance لكل زر وأيقونة وfilter.

### الخاطئ أو الممنوع
- workboard filters شكلية أو client-side على subset ناقص.
- زر intervention يكتب state مباشرة.
- أكثر من Operator ينجز نفس task دون claim/version.
- طلب مساعدة يختفي بلا resolution/readback.
- أولوية hardcoded أو مالية خارج المالك.

### التصحيح المطلوب
- operational registry يربط queue→query→card→actions→permissions→commands.
- server-side filtering/pagination/sorting.
- claim/lease/version وidempotency.
- Platform Control فقط لتغيير policy/rollout، لا حقيقة الطلب.
- إزالة dead boards/routes/components والازدواجية.

### الإضافات المطلوبة
- inbox موحد للطلبات المساعدة.
- SLA breach indicators وتنبيهات.
- audit diff وreason/evidence.
- recovery من operator disconnect/expired lease.

## منطق التشغيل

- projection تنتج work items من order/support/incident events.
- item lifecycle `OPEN | CLAIMED | IN_PROGRESS | WAITING | RESOLVED | EXPIRED`.
- claim lease قابل للاسترداد؛ command يعيد version جديدة.
- resolution لا تغير Order إلا عبر command مالك الرحلة.
- كل Surface يرى request status والردود المسموحة.

## Control Panel

- queues مع counts موثوقة، filters، search، sort، pagination، saved views إن كانت معتمدة.
- card يظهر SLA، الحالة، actor/store/order refs، reason، next actions.
- controls: claim، release، assign، escalate، request info، execute governed action، resolve.
- كل control disabled/hidden وفق permission/state ويملك confirmation للعمليات الحساسة.
- حالات empty/loading/error/stale/partial/permission denied واضحة.

## App Client

- `طلب مساعدة` من Order detail، اختيار نوع، وصف، attachment وفق policy، إرسال، متابعة الحالة، الرد، الإغلاق/إعادة الفتح حسب القاعدة.
- لا يكرر request عند double tap أو offline retry.

## App Partner

- operational requests المرتبطة بالتحضير/التوفر/الطلب.
- controls للرد وتقديم evidence؛ لا يرى بيانات غير لازمة.

## App Captain

- `تعذر التنفيذ`/`طلب دعم` مع reason codes وlocation/evidence المسموح.
- حالة الطلب والرد تظهر أثناء المهمة دون تجميد route.

## App Field

- طلبات الزيارة/التصعيد والمعلومات الإضافية.
- upload evidence واستلام قرار المشغل.

## العقود والبيانات

- work item/read model وsupport request contracts.
- server pagination/filter schema.
- claim lease/version/assignee constraints.
- command audit/outbox/notifications.
- attachments عبر media runtime لا base64/paths محلية.
- operator context isolation.

## الاختبارات الآلية

- two-operator claim race.
- lease expiry/reclaim.
- filter/query effectiveness وpagination.
- unauthorized action/IDOR.
- duplicate assistance request.
- attachment validation.
- SLA clock pause/resume.
- projection rebuild وstale board.
- action registry coverage لكل control.

## التجريب اليدوي

1. ولّد Orders وحالات تنتج عدة queues.
2. اختبر كل filter/sort/search/pagination.
3. طالب نفس item من مشغلين.
4. نفّذ request info من كل Surface ورد عليه.
5. افصل Operator أثناء claim ثم انتظر lease recovery.
6. اختبر action حساس بموافقة ناقصة ثم مكتملة.
7. أعد بناء projection وتحقق من counts.
8. راجع audit/SLA/notifications والـattachments.

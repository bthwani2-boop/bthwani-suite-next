# 28 — سياسة التنفيذ المباشر على فرع العمل

Status: ACTIVE_CANONICAL

**Effective:** 2026-07-26  
**Authority domain:** branch execution, repository writes, task routing  
**Machine-readable contract:** `governance/authority/direct-work-branch-execution-policy.json`

## 1. الغرض

تثبت هذه السياسة أن التنفيذ الافتراضي لأي مهمة GitHub يتم مباشرة على فرع العمل الذي حدده مالك المستودع، دون إنشاء فروع مهام أو Pull Requests تلقائيًا. الهدف هو تقليل التأخير والتكرار وحركة الفروع غير الضرورية، مع إبقاء التحقق متناسبًا مع الخطر وعدم التضحية بالدقة أو سلامة المستودع.

## 2. القاعدة الحاكمة

عندما يحدد المستخدم فرع عمل صريحًا ويطلب التنفيذ:

1. يكون الفرع المحدد هو `SOURCE_BRANCH` و`TARGET_BRANCH` في الوقت نفسه.
2. يقرأ الوكيل ويكتب ويتحقق على ذلك الفرع فقط.
3. يمنع إنشاء أي فرع `task/*` أو `fix/*` أو `feature/*` أو أي فرع وسيط تلقائيًا.
4. يمنع فتح Pull Request تلقائيًا.
5. يمنع تحويل التنفيذ إلى `master` أو أي فرع آخر غير المسمى.
6. تجمع التغييرات المنطقية المتصلة وتدفع في أقل عدد آمن من عمليات الكتابة، ثم ينفذ التحقق بعد آخر كتابة ذات صلة.

## 3. متطلبات التنفيذ المباشر

قبل أول كتابة يجب:

- تثبيت المستودع والفرع المسمى وSHA الحالي.
- حصر المسارات المسموحة والمتأثرة.
- التأكد أن أمر المستخدم الحالي يطلب تنفيذًا فعليًا، لا تحليلًا فقط.
- استخدام كتابة مشروطة على SHA الملف أو الفرع لمنع الكتابة فوق حركة متزامنة.

بعد آخر كتابة يجب:

- إعادة حل رأس الفرع.
- التحقق أن التغييرات موجودة على الفرع نفسه.
- تشغيل الفحوص المستهدفة المناسبة لدرجة الخطر.
- الإبلاغ عن SHA النهائي والمسارات المتغيرة والفحوص والقيود المتبقية.

## 4. الاستثناءات الوحيدة

لا يجوز إنشاء فرع جديد أو Pull Request إلا في إحدى الحالتين التاليتين:

1. أمر بشري صريح في المهمة الحالية يطلب إنشاء الفرع أو Pull Request بالاسم أو الغرض.
2. استحالة الكتابة المباشرة بسبب حماية الفرع أو نقص صلاحية، وفي هذه الحالة لا ينشئ الوكيل فرعًا بديلًا من تلقاء نفسه؛ يعيد `BLOCKED_EXTERNAL` أو `NEEDS_EVIDENCE` مع سبب واضح، إلى أن يصدر أمر بشري صريح بالمسار البديل.

التاريخ السابق لا يعد إذنًا دائمًا لإنشاء الفروع. الموافقة العامة السابقة لا تستبدل أمر المهمة الحالية.

## 5. المهام عالية الخطورة

الماليات، المصادقة، الأسرار، عزل المستأجرين، قواعد البيانات، migrations، CI، البنية التحتية، الإصدار والإنتاج لا تفرض فرع مهمة تلقائيًا. تنفذ على فرع العمل المسمى مع رفع درجة التحقق والمراجعة حسب الحوكمة. إذا كانت حماية GitHub تمنع ذلك، تطبق قاعدة الاستثناء الثانية دون تجاوز الحماية.

## 6. التزام السرعة والدقة

- التعديل الصغير: كتابة مباشرة وفحص مستهدف.
- التعديل المتوسط: كتابة مباشرة وفحوص affected مرتبطة.
- التعديل العميق: كتابة مباشرة وفحوص عميقة مرتبطة بالخطر.
- لا تستخدم الفروع كبديل عن التشخيص أو التحقق.
- لا تشغل فحوصًا غير منطبقة لمجرد أن التنفيذ مباشر.
- لا تخفف فحصًا مطلوبًا لمجرد طلب السرعة.

## 7. قواعد منع التداخل

- عند تحرك رأس الفرع بصورة غير متوقعة قبل الكتابة، يعاد التثبيت والتقييم قبل المتابعة.
- يمنع force-push وإعادة كتابة التاريخ.
- يمنع إسقاط تغييرات متزامنة أو استبدال ملف ببيانات مبنية على SHA قديم.
- تكتب الملفات المشتركة والمتولدة والمهاجرات بشكل متسلسل.

## 8. علاقة هذه السياسة ببقية الحوكمة

هذه السياسة تحكم اختيار فرع التنفيذ فقط. لا تلغي فصل السلطات أو أدلة الأمن والماليات والعزل والإصدار والإنتاج. عند التعارض، يطبق ترتيب السلطة في `governance/authority/authority-precedence.json`، وتبقى التعليمات الصريحة للمهمة الحالية في المرتبة الأولى ضمن حدود السلامة والصلاحيات.

## 9. القرار الافتراضي

```text
NAMED_WORK_BRANCH
→ PIN EXACT SHA
→ EXECUTE DIRECTLY ON THE SAME BRANCH
→ TARGETED OR DEEP VERIFICATION BY RISK
→ RE-PIN FINAL SHA
→ REPORT SCOPED RESULT
```

النتيجة الافتراضية: **لا فرع مهمة، لا Pull Request، ولا دمج تلقائي.**

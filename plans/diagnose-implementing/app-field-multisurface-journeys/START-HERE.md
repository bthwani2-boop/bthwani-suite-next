# Start here — App Field Multi-Surface Journey Diagnosis and Execution

## Multi-surface rule

This dossier treats `app-field` as an entry point into one full-stack, unified, multi-surface operating system. Every file, task, check, and result must cover the affected behavior on `control-panel`, `app-client`, `app-partner`, `app-captain`, and `app-field`. A journey or one of its twenty-four slices may not be diagnosed, changed, verified, or closed in isolation. A surface with no direct control must still be assessed as a reader, observer, downstream consumer, permission boundary, or explicitly evidenced non-participant.

## Objective

Diagnose and plan the complete app-field operating model as one cross-surface system, covering every related journey, page, control, user experience, UI/UX state, flow, binding, API, integration, contract, data effect, failure mode, readback, and dependent result across control-panel, app-client, app-partner, app-captain, and app-field without isolating any journey or slice.

## Required reading order

1. `MANIFEST.json`
2. `GLOBAL-DIAGNOSIS.md`
3. `COVERAGE.json`
4. `EXECUTION-ORDER.json`
5. the first ready stage whose dependencies are complete
6. that stage's `DIAGNOSIS.md`, `EXECUTION.json`, and `VERIFICATION.json`
7. write actual outcomes only to that stage's `RESULT.json`
8. continue in dependency order
9. complete `CLOSURE.md` only after all stages pass on the same implementation SHA

## Mandatory execution behavior

- Trace every control from actor and route through identity, generated client, API, handler, state machine, transaction, event/job/provider, projection, and readback on every required surface.
- Preserve DSH as operational truth and WLT as sole financial truth; surfaces must not call WLT directly.
- Map every visible label, icon, form, tab, deep link, notification action, retry, offline operation, and accessibility name to a real command/query and a persisted or explicitly non-persisted result.
- Test loading, empty, validation, forbidden, blocked, conflict, stale version, offline, reconnecting, partial dependency failure, unknown result, success, refresh, restart, reinstall, and terminal states where applicable.
- Execute all twenty-four journey slices as one integrated checklist inside each stage. Do not create separate product code or separate closure claims named after this dossier's stages.
- Do not claim complete verification from static checks alone. Physical-device, provider, production-like data, and manual cross-surface evidence remain required gates.

# U005 — field-operations-offline

## Integrated multi-surface scope

This stage is not a standalone journey and does not own a standalone slice. It applies the complete twenty-four-slice contract to one engineering concern while preserving the full chain across `control-panel`, `app-client`, `app-partner`, `app-captain`, and `app-field`. Every changed writer must identify all readers; every visible state must identify its command or query, authoritative owner, persisted effect, failure codes, retry policy, readback, and effect on the other surfaces. A surface without a direct control remains in scope for permission boundaries, projections, freshness, masking, denial, and non-disclosure.

## Objective

Close assigned work, visit, check-in, checklist, verification, evidence, escalation, work queue, audit, support, offline queue, conflict, unknown result, and reconnect behavior across all readers and writers.

## Current diagnosis

The pinned repository contains meaningful field runtime, route, shared-brain, API, backend, governance, and control-panel structures, but those structures are distributed and cannot be accepted independently. The 107-journey registry requires zero unmapped controls, zero parallel truths, manual acceptance, runtime readback, and same-SHA evidence. The field final vision extends beyond route presence to assignment-scoped work, offline evidence safety, partner/store/catalog orchestration, audit, support, and financial custody. The current code demonstrates secure session setup, readiness gates, deep links, offline mutation replay with idempotency, and detailed backend business errors. It does not by itself prove generated-client authority, complete state-machine coverage, specific UX recovery, encryption and expiry of every offline record, cross-surface convergence, real native notification behavior, or physical-device accessibility.

## Root risk

The central risk for `visits-checklists-evidence-escalation-offline-convergence` is false local completion: a field action may appear successful while another surface remains stale, a permission change is not revalidated, a backend reason is reduced to a generic message, an offline replay duplicates an effect, a catalog or financial value is copied locally, or a route exists without a complete control-to-transaction-to-readback chain. Fixes must therefore start at truth, contract, and state ownership before presentation, and must end with same-SHA readback on every required surface.

## Twenty-four-slice application

The stage must document and verify truth ownership; actors and permissions; entry and deep links; visible actions and states; controllers; generated client binding; contracts and validation; backend transport; orchestration; state machine; persistence and scope; events, jobs, retries, and idempotency; providers, secrets, and media; DSH/WLT boundaries; control-panel operation; audit and support; security and privacy; failure, conflict, offline, and recovery; UI system and accessibility; tests and builds; release and rollback; manual acceptance; defect decisions; and final evidence. These are one checklist. None is delegated to an isolated later journey.

## Dependencies

U001, U002, U003

## Exit condition

Exit is allowed only when the stage's tasks and required checks pass, all discovered defects are linked to a canonical fix or explicit external blocker, every affected surface has a recorded before/during/success/failure/refresh/restart result, and no result file claims final closure. Static proof may advance the stage, but native-device and provider evidence remains reserved for the final same-SHA verification stage.

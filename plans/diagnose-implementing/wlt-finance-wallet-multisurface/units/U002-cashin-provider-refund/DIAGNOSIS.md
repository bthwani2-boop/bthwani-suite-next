# U002 Diagnosis — Cash-In, Provider and Refund

Current payment code contains two mechanisms worth preserving: a database claim before external mutation to close duplicate concurrent calls, and explicit `provider_result_unknown` handling when a request may have reached the external system. The weakness is the abstraction boundary. The payment layer posts to hard-coded card authorize/capture URLs through a generic provider transport, while the current financial product requires official-wallet Cash-In for customer and captain funding with provider-specific capabilities hidden behind a domain contract.

The provider directory already has mock/production structure, circuit breaking and inquiry support, so the correct change is adapter evolution rather than replacement. Introduce a deterministic `FinancialRailRouter` and `ProviderRegistry`, one active real provider at launch, and a domain `CashInRail` contract. Mock remains valid for local/CI, sandbox for provider contract testing, and production must fail closed if no approved real adapter is available. A production provider failure must never fall back to mock, and an ambiguous external mutation must be reconciled before any alternate route can move the same money.

Captured Cash-In must post according to the server-owned financial purpose: customer top-up credits the customer wallet, captain top-up credits the captain wallet, while order payment follows its own allocation. Provider callbacks are evidence only after provider-specific verification/normalization. Refunds must return to the authoritative original source where supported and may not silently convert an external refund into internal credit. Real provider credentials or undocumented endpoints are outside this package until an actual contract/sandbox exists.

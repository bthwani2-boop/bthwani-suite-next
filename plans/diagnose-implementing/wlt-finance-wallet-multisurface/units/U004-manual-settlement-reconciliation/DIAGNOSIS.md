# U004 Diagnosis — Manual Settlement, Reconciliation and Close

The existing payout/settlement area contains reusable controls but the active semantics are wrong for the current operating model. `payout_governance.go` still treats destination preference as bank/mobile-money/manual and stores bank/IBAN fields. Provider-processing code and the control-panel payout UI imply that BThwani can submit payouts to an external provider. The canonical product decision instead separates destination from execution: partner/captain/field select a supported official-wallet destination that finance verifies; after payout approval, finance executes the transfer manually in BThwani's official external wallet application. The platform records, verifies and reconciles that external action but does not perform it through an automated CashOut API.

Security depends on freezing facts before execution. Destination changes require a new verified version. Approval must bind beneficiary, destination version, amount, currency and policy context to an immutable snapshot. Approved snapshots are grouped into an immutable SettlementBatch with control totals/hash; XLSX is an audited execution artifact, never a database. The executor records external reference/evidence, a separate authorized checker/reconciler verifies it, and completion requires agreement with an authoritative official-wallet statement/record. Duplicate references and mismatches open blocking exceptions.

The current settlement package already has evidence and governed-source primitives, so reuse them. Add Treasury reconciliation of BThwani's external wallet accounts as control facts, SettlementAuditPack lineage and DailyFinanceClose gates. Existing provider-payout rows and bank-oriented data require forward migration and historical retention. Automated cash-out must be disabled/removed from active routing without deleting evidence needed to audit old transactions.

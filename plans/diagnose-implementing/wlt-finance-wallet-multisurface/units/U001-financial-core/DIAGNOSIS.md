# U001 Diagnosis — Canonical Financial Core

The repository already has the correct financial ownership direction: WLT owns wallet/ledger truth and `PostLedgerTransaction` is the canonical double-entry write path. The change must therefore extend this kernel instead of creating a second balance store. Static evidence shows operator-context isolation, balanced-entry validation and idempotent reference matching are present and valuable. The material gap is semantic: account classification is too narrow for external settlement cash and processing expense, and payment/accounting behavior is not driven by an explicit server-owned financial purpose and order allocation.

The capability Product Truth also requires one internal wallet per actor, one server-owned PaymentAllocation for applicable orders, no delivery-fee double counting, explicit withdrawal eligibility, and opening/correction movements through ledger history. These facts cross WLT database, contracts, DSH references and generated clients. The root implementation strategy is forward-compatible: add canonical enums/records and account classifications, backfill only from authoritative persisted facts, switch writers/readers, verify conservation and balance invariants, then retire obsolete compatibility fields only after mixed-version safety is proven. Applied migration history must not be rewritten.

This unit deliberately does not implement provider calls, captain COD lifecycle, payout execution or UI. It establishes the financial vocabulary and data invariants those later units depend on. Any direct SQL balance mutation discovered during implementation is a blocker and must be routed through the ledger rather than grandfathered as compatibility.

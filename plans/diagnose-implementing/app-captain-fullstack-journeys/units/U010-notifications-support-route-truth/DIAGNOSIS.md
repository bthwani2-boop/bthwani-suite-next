# U010 — notifications-support-route-truth

Captain notifications have a full device lifecycle: permission request, device identifier in SecureStore, Expo token registration, token rotation, endpoint deactivation before session end, notification response handling and safe scheme/HTTPS action URLs. This is not just a bell screen. Backend endpoint ownership must be actor-scoped, logout must invalidate the device endpoint, stale tokens must not remain active indefinitely, and notification actions must not open unauthorized Captain state after session loss.

Support has a confirmed route contradiction. The Captain registry declares order chat while one renderer path reports messaging unavailable and support subroutes use the actual CaptainOrderSupportConversationScreen. A reachable route cannot simultaneously be “supported” and “disabled.” The route/caller/deep-link census must choose one canonical behavior and remove dead aliases/copy after proving callers.

The diagnosis also found Captain support/operations presentation containing static demonstration-like Captain/order/COD/tier values. If reachable, that is fabricated product truth and a release blocker, especially for financial/operational values. The unit replaces reachable static data with authorized canonical readback or removes the dead surface. Captain support remains assigned-order scoped; internal operator notes and rescue authority remain hidden, and support must not mutate WLT financial state.

# U001 — authority-scope-inventory

This unit exists because the previous Captain package was structurally too coarse and stale. The current scope is not “all DSH/WLT”; it is every reachable app-captain route, state and operation plus only those external writers/readbacks whose state directly governs or reflects a Captain outcome. The baseline is rebound to the current BB head. The route registry, app runtime, Identity, Workforce, DSH dispatch/handoff/tracking/proof/support and WLT finance are treated as separate owners rather than one undifferentiated stack.

The inclusion rule is strict: include a component when it authenticates the Captain, provisions/gates the Captain, mutates or reads Captain operational state, changes a Captain assignment/delivery/proof/support/notification/financial result, or is a cross-surface writer/readback required to prove that same result. Generic proximity is insufficient. This excludes independent client/partner/field/operator product journeys even when they share libraries.

Execution must re-resolve BB before every write batch. Any branch movement is classified as disjoint, related, overlapping, conflicting or authority-changing. Related Captain movement invalidates affected assumptions and is re-diagnosed. No closure evidence from an older candidate can be promoted to the new head. The final package therefore begins with exact inventory and ends with same-SHA proof rather than relying on package prose.

## Closure boundary

Repository authority and current Product Truth/code evidence define scope; the package is derived support and cannot invent policy. The unit remains open until all required checks are executed on the exact candidate, all known fixable Captain defects in this concern are removed, cleanup is complete, and later units have not invalidated its evidence.

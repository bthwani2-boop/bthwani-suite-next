# Global diagnosis — exhaustive Captain-bounded closure

The former six-unit package was too coarse. Current source shows app-captain is a multi-owner runtime: Identity owns actor/session/surface authorization; Workforce owns Captain employment/profile/readiness lifecycle; DSH owns availability, fleet relationship, dispatch eligibility, assignment, custody, delivery, tracking, proof, notifications and support operational state; WLT exclusively owns monetary truth; Expo/native configuration owns device capability declarations. Partner, client and control-panel enter only where they write/read the same Captain outcome.

The rebuilt package uses twelve non-overlapping concerns. Native/runtime and route-registry parity are explicit. Identity and Workforce are separate. The confirmed availability/service-mode defects are isolated from fleet eligibility. Fleet/eligibility is separate from assignment/custody. Location/tracking is separate from PoD/media. Notifications/support is separate from both. Finance remains its own high-risk WLT unit. Final cleanup/red-team is a separate exact-SHA closure gate.

App-captain currently gates through Identity plus Workforce/readiness, registers push, and mounts a DSH Captain surface with account/profile/finance/orders/documents/shifts/settings, inbox/detail, order chat, notifications, support, pickup/dropoff, PoD and map/navigation routes. The mobile manifest also declares secure storage, notifications, camera/media, foreground/background location, maps, TaskManager and updates. Every reachable route/capability now has an explicit execution owner.

Confirmed functional defects include an availability model fixed to unavailable with mutations failing because no DSH contract is wired; local store-courier mode influencing whether PoD/exception presentation is available; background-location native declaration without established governed background tracking; support/chat route contradiction between registered order chat and disabled renderer behavior; and support/operations presentation requiring elimination of static demonstration-like Captain/order/COD/tier truth if reachable.

Dispatch eligibility must combine accreditation, persisted availability, unexpired WLT financial eligibility, profile freshness, absence, service area and capacity, with transactional recomputation at assignment. Partner fleet is included only because its relationship directly affects Captain work. Assignment requires mandatory fail-closed kill-switch configuration, actor-scoped/idempotent accept/decline/reassign and concurrency/expiry behavior. Store pickup requires bilateral partner plus Captain evidence before picked_up, with replay, exception and reassignment protection.

Location/tracking binds device input to authenticated Captain plus active assignment and must recover from weak/ambiguous network outcomes without fabricated movement. PoD/media is a distinct proof transaction: completion derives from canonical DSH proof state, not upload/UI success. Delivery exceptions remain server-owned. Notifications include permission, device endpoint registration/rotation, logout deactivation, safe action routing and delivery audit. Support stays assigned-order scoped with no internal operator authority exposed.

WLT remains the sole financial authority. Existing top-up infrastructure supports server-derived captain_topup and governed authorize/capture/credit with unknown-result reconciliation, but a reachable Captain top-up consumer must be proven or implemented as a bounded WLT client. Stale WLT Captain bridge presentation must be migrated or removed. Funded COD reserve/release/finalize and collect/remit semantics must be explicitly mutually exclusive per order/effect to prevent double liability. Earnings, payout destination, payout eligibility, ledger and reconciliation are WLT-derived.

The broad `smsm-dsh-wlt-journeys` package is used only for discovery. Official Expo documentation and OWASP MASVS inform native/security verification mechanics but cannot override BThwani Product Truth or enlarge scope. Final closure remains forbidden while any known fixable Captain defect, stale/demo truth, permission overreach, actor leak, duplicate state writer, financial ambiguity, dead Captain residue, broken contract or unverified native/runtime path remains.

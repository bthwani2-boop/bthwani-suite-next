# U006 — support, ratings, notifications and preferences

These interactions look secondary in the client UI but contain several ownership and authorization boundaries. Support/rescue Product Truth is still `DISCOVERY`: a client ticket and conversation must be owned by the authenticated actor, internal operator notes must never leak, messages and state transitions must be retry-safe, and an operator rescue action may expose a DSH outcome but cannot manufacture WLT financial truth. Partner/Captain/control surfaces enter only for the exact support/order consequence shared with the client.

Ratings are server-owned post-order effects. The client may render a rating gate, but eligibility depends on the authoritative order/actor/state rules and submission must be idempotent. Recent branch changes materially touched DSH ratings, so the old package evidence is invalid. A duplicate tap, restart or stale order version must not create multiple ratings or apply a rating to an ineligible/wrong order.

Notifications span Identity/device and DSH object state. Push registration belongs to the active actor/session/device lifecycle and must be invalidated/rebound on logout or subject change. A notification delivery is not business truth: opening a deep link must re-authorize the referenced order/support object against current canonical state. Mark-read/delete/preference mutations must be actor scoped, replay-safe and reload committed state; offline/unavailable delivery must not fabricate success.

The final evidence bar is intentionally end-to-end: app-client operational/lifecycle contracts, targeted support/ratings/incident Go tests, DSH database constraints, full runtime smoke, mobile transport contracts and a physical-device scenario covering wrong actor, hidden notes, duplicate rating/message/preferences, stale links, logout token changes, offline recovery, RTL and accessibility.
